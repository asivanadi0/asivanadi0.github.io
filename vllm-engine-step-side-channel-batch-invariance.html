Two Models, One vLLM Engine: The Step Size Is a Shared Wire

26 November 2026 · Anpoo Sivanadi

Most of us treat an inference engine as stateless from the point of view of a single request. Your prompt goes in, your tokens come out, and the other requests in the batch only change how long you wait. A post by Niranjan Deshpande and David Africa, with code and per-round results on GitHub, shows that this is not true at the bit level, and that two models sharing one vLLM server can turn that into a working channel with no network and no shared files. It picked up wide coverage this week, including Tom's Hardware.

I am less interested in the AI safety framing than in what it says about the serving stack, because the mechanism is the same batch dependence I wrote about in the Detent post. So I read the repo's result files and checked the mitigation runs myself.

1. The setup

Unless noted otherwise, everything runs Qwen3-8B on vLLM 0.33.0 on a single NVIDIA L40S. The engine in the game scripts is configured with a 2,048-token budget per engine step and up to 64 concurrent sequences. Two players, Alice and Bob, can each call tools and send requests to the server, but cannot message each other.

The root cause is simple. vLLM batches many requests into one engine step and the GPU libraries it calls pick a kernel based on how many tokens that step processes. Different kernels associate the floating-point sums differently, so the same request produces slightly different activations depending on step size. The authors count about 9 size classes on the L40S. The differences almost never change output text, but they are deterministic, and that is enough to read them.

2. Two channels

Step sizing. To send a 1, Alice makes a tool call that ingests a long document, which pushes the step into a different size class. Bob, if he is computed in that same step, sees the other kernel's rounding in his own activations. To send a 0, Alice stays quiet. Timing turns out to be easy to hit: if Alice queues a 6,126-token document (two full 2,048-token steps plus 2,030), the scheduler finishes her chunks first and Bob's first 18 tokens land in the third step. In their timing runs Bob saw the signal in 20 of 20 trials at any delay shorter than the document read, about 0.4 s for 6,126 tokens and 4 s for 24,558.

KV cache message board. vLLM's prefix cache stores KV in 16-token blocks keyed by a hash of every token from the start of the prompt, and a cached block keeps the rounding of the step that computed it. Alice has a helper model read an agreed "mailbox" text inside a long prompt, so its KV is computed under the big-step kernel and cached. Later, Bob's helper reads the same mailbox in a small step. If the cache hit carries big-step rounding, Alice wrote it. This one does not need the two to run at the same time, only a shared prefix and a helper on the same server.

3. The results that matter

  • With a fine-tuned reader (the last two layers of Bob's helper trained to spot the signal), Bob named Alice's color out of 8 in 1,221 of 1,221 games over the message board, and 455 of 455 over step sizing.
  • In an untrusted-monitoring setup, a policy paired each harmful action with a long document read. A monitor fine-tuned to score 0 under a full step let 354 of 354 signaled attacks through while still catching 85 to 92% of honeypots and flagging none of 1,596 benign actions.
  • Without any fine-tuning, an unmodified GLM-5.3 at low effort decoded the message board from helper log-probs at 100% when given the full protocol and baselines, 65 to 66% with only a log of earlier rounds, and 17% when it had to choose which mailboxes to check. Chance is 12.5%.
  • Both channels worked on SGLang, LMDeploy and TensorRT-LLM as well as vLLM. Step sizing worked on A40, RTX 4090, RTX 5090 and H100. A reader trained on one GPU did not recognize the signal on another.

Load is the big caveat. Replaying the Azure LLM inference trace in the background, the message board won 100%, 99%, 90% and 49% of games at 0.1x, 0.25x, 0.5x and 1x replay speed. Step sizing fell to 39% and 23% at 0.1x and 0.25x. On a busy engine, everyone's steps are big.

4. What I checked in the repo

The result folders include per-action rows, so I recomputed the monitor numbers rather than trusting the chart. Each condition has 576 actions, 177 harmful and 399 benign.

  • Default kernels, signal on: 0 of 177 harmful actions flagged in each of two runs, which is the 354.
  • Default kernels, signal off (the honeypot case): 152 and 151 of 177 flagged, about 85 to 86%.
  • VLLM_BATCH_INVARIANT=1: 154 of 177 flagged with the signal on and 154 of 177 with it off.

My take: the batch-invariant result is cleaner than "detection restored to 87%" suggests. In that run, the monitor's log-probs over the ten score digits were identical between a full step and a partial step on all 576 actions. With default kernels, only 6 of 576 matched. That is a direct test of the property the fix claims.

The mitigation runs for the color games say the same thing. With batch invariance on, the message board won 16 of 120 games (13.3%) and step sizing 11 of 69 (15.9%), both near the 12.5% chance line. With per-agent cache_salt, the message board won 15 of 120, exactly chance. My read: batch invariance closes the message board too, because the cached block no longer carries a step-dependent fingerprint.

5. What the fixes cost

Both fixes exist today and both are opt-in.

Batch invariance. vLLM's batch invariance docs mark the feature as beta, supported on NVIDIA compute capability 8.0 and up, AMD gfx90a, gfx942 and gfx950, and Intel XPUs with Triton. Turning it on disables FlashInfer, AITER and QuickReduce all-reduce under tensor parallelism, and on some GPUs runs without torch.compile, using breakable CUDA graphs. The docs say plainly that it "may impact performance." For a number, the Detent paper measured the built-in deterministic modes at 1.67 to 10.3x stock latency per output token on four H100s, and its own pinned-selector approach at 1.04 to 1.17x.

Cache salting. Per the vLLM security docs, cache_salt is mixed into the hash of the first KV block, so only requests with the same salt share prefix blocks. The docs ask you to treat the salt as a secret (for example 256 random bits), scope it to the boundary you want, and accept that it reduces cache hit rate. This is the same mechanism already recommended for the prefix-cache timing leak (CVE-2025-46570; the prefix cache paper it cites reports ROC AUC 0.99 at 8-token prefixes). The same page also says vLLM "does not provide isolation between tenants that share the same server process."

6. How I would act on it

  • Monitors and policies on separate engine instances. The authors say this "closes nearly every side channel," and it costs only a little packing efficiency. If you run an agent platform where a judge model sits on the same engine as the agents it grades, this is the cheapest fix on the list.
  • Salt at the gateway, not in the client. Generate per-tenant secrets in the layer that authenticates callers, so no caller can choose another tenant's salt.
  • Batch invariance where you need determinism anyway. On-policy RL and rerunnable evals already want it. For latency-bound production traffic, measure the cost on your model before turning it on fleet-wide.
  • Add a bit-diff check. The authors suggest it in their comments: run the same request on a full server and an empty one and compare outputs bit for bit. That catches a new optimization reopening a channel, and it doubles as a determinism regression test.

7. What this does not show

  • The setups are contrived on purpose. The players were told the protocol, the readers were fine-tuned, and in some games scripts played Alice and Bob.
  • Most numbers come from an otherwise idle server, and accuracy drops hard under realistic traffic.
  • Everything is single-GPU, Qwen3-8B class. I have not seen it tested with tensor parallel, expert parallel or disaggregated prefill.
  • The trained reader layers are not published, so the fine-tuned results cannot be rerun from the repo alone. The per-round data I used is there.
  • I have not run any of this myself.

My take

This is a reminder that "shared server" means shared state, even when the state is just which kernel ran. For anyone hosting multiple agents or tenants on one engine, the useful output of this work is not a new threat model so much as a short checklist: separate instances for anything that must not collude, salted prefix caches across trust boundaries, and batch invariance where its cost is acceptable. The repo's result files are the best part, because they show the fixes doing exactly what they claim.
