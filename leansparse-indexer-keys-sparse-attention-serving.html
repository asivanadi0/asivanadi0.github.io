The Indexer Is the New KV Cache: LeanSparse and Million-Token Sparse Attention Serving

8 November 2026 · Anpoo Sivanadi

Sparse attention was supposed to make long context cheap. Each query reads a few hundred historical positions instead of the whole history, so compute stops growing with context. Memory doesn't follow. A token one query skips can be the token the next query needs, so the full history still has to live somewhere.

LeanSparse: Memory-Efficient Serving for Native Sparse-Attention LLMs, posted Nov 3 by a group at UC San Diego, points at what's left once you do that. The indexer, the small learned scorer that picks which positions attention reads, keeps its own keys for every historical position, and those stay on the GPU. At long context they become the biggest per-request allocation. LeanSparse fixes that and a second problem in prefill, and it's measured on real hardware: four H100s, tensor parallel, SGLang, serving DeepSeek-V4-Flash.

1. Where the memory actually goes

DeepSeek-V4-Flash alternates two attention layer types. Compressed sparse attention (CSA) layers compress history at a stride of four and use DeepSeek Sparse Attention: an indexer scores every eligible compressed position and selects up to k = 512 for attention. Heavily compressed attention (HCA) layers compress at a stride of 128 and attend to everything left. CSA dominates historical storage, so that's where both HiSparse and LeanSparse focus.

Each CSA layer keeps two separate things per position: an indexer key, used only for scoring, and the compressed KV that attention actually reads. HiSparse offloads the KV and keeps a 4K-entry hot KV buffer per layer on the GPU. It keeps all indexer keys resident, because the indexer has to score the whole history every decode step. Moving them to host would mean copying the full history across the host link for every generated token.

The paper's Figure 1 makes the cost concrete. At 512K tokens of context, the FP8 indexer keys for one CSA layer take 7.2x the space of that layer's 4K-entry hot KV buffer. Shrinking attention KV just made the indexer the larger allocation, and it still grows linearly with context.

The second problem is prefill. Decode benefits from the hot buffer because consecutive steps keep selecting many of the same positions. A prefill chunk processes many queries at once, and together they can select from a much wider slice of history, and a newly admitted request has no warm buffer anyway. HiSparse keeps the full KV history in HBM during prefill. When prefill and decode share a GPU, a new request may fit fine once it's decoding but not while it's prefilling. You either make it wait until decode requests finish, which hurts time to first token, or reserve HBM for prefill, which sits idle when nothing is prefilling. Disaggregating prefill and decode avoids that but duplicates weights, which hurts most when HBM is already tight.

2. Coarse-to-fine indexing for decode

LeanSparse moves all indexer keys and compressed KV to host memory and keeps a compact searchable copy of the indexer keys on the GPU. The compact copy is product quantization. Each 128-dimensional indexer key is split into 32 four-dimensional subvectors, and each subvector is stored as a one-byte index into a per-layer codebook of 256 centroids, trained offline. That's 32 bytes per position instead of 132 bytes for the FP8 key plus its scale.

Each decode step then runs in three passes:

  • Coarse search. Score the whole history using the PQ codes, applying the indexer's weighted per-head ReLU aggregation with centroids standing in for the real subvectors. Keep C = 2048 candidates, four times the 512 attention needs.
  • Exact rescoring. Fetch the original indexer keys for those candidates from a per-request GPU cache, or from host on a miss, and compute real indexer scores. Pick the final top 512.
  • KV retrieval. Pull the selected compressed KV from a separate KV cache, or from host on a miss, and run attention.

Two details matter. First, the indexer key cache and KV cache are separate, because they serve different sets. Positions that keep showing up as candidates but don't make the final 512 still need their indexer keys cached, even though attention never reads their KV. Per request, LeanSparse holds 4K indexer keys and 2K KV entries per CSA layer. Second, before fetching, it drops low-scoring misses: a candidate that isn't cached and whose approximate score is below the 512th-largest score minus one sample standard deviation never crosses the bus.

The over-fetch is what keeps accuracy. In an offline analysis on Open-SWE traces, picking the top 512 straight from PQ32 scores recovers 77.41% of the exact indexer's selections on average. Keeping 2,048 candidates and rescoring with the real keys recovers 99.49%. The PQ pass only has to avoid throwing away good candidates; the exact keys make the final call.

3. Layer-wise streaming for prefill

For prefill, the observation is that a chunk extending an existing prefix consumes that prefix one layer at a time, and the prefix's indexer keys and compressed KV were already computed. So LeanSparse keeps two GPU buffers and alternates them. While CSA layer N computes out of buffer A, a copy stream loads layer N+1's prefix state into buffer B. It loads full compressed KV along with the indexer keys, so the transfer can start without waiting on selection, at the cost of moving some KV attention won't read. The prefill allocation drops from one buffer per CSA layer to two.

Whether the copy hides behind compute is a bandwidth question, and the paper models it. For a 512K-token prefix on H100 SXM with TP4, a 4K-token chunk gives a 5.2 ms overlap window (the current CSA block's remaining work plus the next HCA block, including both MoE FFNs, which contribute 0.36 ms). Loading the next layer plus writeback takes 2.9 ms at 32 GB/s of effective host bandwidth per GPU, leaving about 2.4 ms of slack. That assumes full compute efficiency and no startup delay, so treat it as a sizing guide.

4. What it measured

All runs use DeepSeek-V4-Flash on four H100s with tensor parallelism in SGLang.

Long-context decode against HiSparse. Contexts of 200K, 512K and 950K tokens, built from LongSWE-Bench, no prefix reuse, steady decode measured over 2K new tokens per stream at each system's maximum concurrency.

Context HiSparse max requests LeanSparse max requests HiSparse tok/s LeanSparse tok/s
200K 76 156 2,371 3,216
512K 36 96 1,274 2,022
950K 19 56 687 1,474

That's 2.05x to 2.95x the concurrency and 1.36x to 2.14x the decode throughput. Throughput rises less than concurrency because more streams make each step longer.

The equal-concurrency step time is the honest part. At 200K, LeanSparse is 3.8% slower per step (33.3 ms vs 32.1 ms): the PQ pass costs more than it saves when the history is short. At 950K it's 19.6% faster (22.2 ms vs 27.6 ms), because HiSparse's exact scoring grows with context while LeanSparse caps exact scoring at 2,048 candidates.

Multi-turn agent traces against ECHO. 128 long-context sessions from NVIDIA's Open-SWE-Traces, arriving at 120 per minute, with tool waits reconstructed, 4K prefill chunks, prefix caching and mixed prefill/decode batches, up to 128 active requests. HiSparse only supports disaggregated serving, so it's not in this test. The ECHO baseline is the authors' own implementation, since ECHO's release doesn't support DeepSeek-V4.

  • Median time to first token fell from 21.58 s to 0.60 s; p95 from 28.19 s to 1.74 s.
  • Median time per output token rose from 66.4 ms to 81.7 ms, from bigger decode batches and earlier prefill admission.
  • Median session completion fell 17.7% (1,418.9 s to 1,168.0 s), and aggregate throughput rose 10.2%.

That's the trade: many more streams and much faster starts, with each stream a bit slower.

Accuracy. At a 256K context limit with greedy decoding, LeanSparse stays within half a point of stock SGLang: GSM8K 95.83 vs 95.38, multi-key needle-in-a-haystack 100.00 vs 100.00, LongBench v2 50.62 vs 50.87, two-needle MRCR 90.62 vs 90.19. HiSparse scored 96.00 on the needle test in the same table. McNemar tests found no significant difference on GSM8K or LongBench v2.

5. What I'd keep in mind

  • One node, one model. Everything is four H100s with TP4 and DeepSeek-V4-Flash. Hosts with more PCIe or C2C bandwidth per GPU change the prefill overlap math, and GPUs with more HBM move the point where indexer keys start to hurt.
  • The coarse pass still scales with context. PQ codes are about a quarter the size of FP8 keys, but they still grow with history, and the scan touches all of them every step.
  • Short context isn't the target. At 200K the per-step cost is slightly worse. The payoff starts where indexer keys dominate memory.
  • Recall isn't 100%. Rescoring can't bring back a position the coarse pass or miss filter dropped. I'd want to see recall on workloads that don't look like coding agents.
  • The prefill overlap numbers are modeled, and the multi-turn baseline is a reimplementation.

The broader lesson is about where memory goes as models adopt trained sparse attention. Once KV is offloaded, the selection metadata becomes the resident cost, and the selection doesn't need full-precision keys to be good enough to shortlist. If you're sizing nodes for DeepSeek-V4-class models at hundreds of thousands of tokens of context, count indexer keys per layer separately from KV. They're a separate budget now.
