A first look at NVIDIA Cluster Readiness Engine

2 September 2026 · Anpoo Sivanadi · based on v0.4.0 (21 Sep 2026)

Node Ready is not the same as GPU-cluster ready. NVCRE runs real communication and training workloads, then reports which nodes fail and why.

I’m a Staff Software Engineer. I spend a lot of time thinking about the gap between “the control plane says this node is fine” and “this cluster can actually finish a distributed GPU workload.” That gap is exactly what NVIDIA Cluster Readiness Engine (NVCRE) targets.

A Kubernetes node can be Ready while the distributed AI stack on it is not. The kubelet is healthy. The API server can reach it. A device plugin advertises nvidia.com/gpu. None of that proves that GPUs across several nodes can form an NCCL communicator, move data at the expected rate, finish a multi-node training job, or tell you which node is at fault when they cannot.

This note is a practitioner reading of the product from the official v0.4.0 README, first-certification guide, certify-a-cluster docs, and deployment guide. It is not a lab write-up of a cluster I ran, and it is not a contribution recap.

What NVCRE is

NVCRE is an Apache-2.0 Go Kubernetes controller that certifies GPU clusters before production workloads land on them. New GPU clusters often contain faulty nodes, and those faults show up under real distributed load. NVCRE runs real training and communication workloads across topology-aware node groups, measures goodput and bandwidth, detects hardware failures, and reports every bad node with a reason. Quarantine stays with your platform: NVCRE never cordons, taints, or otherwise modifies a node.

The audience is platform and infrastructure teams that bring up, validate, or resell GPU clusters.

From the v0.4.0 feature list:

  • A certification catalog with NCCL tests and multi-node training
  • Platform and GPU architecture detection
  • Goodput from training logs via configurable LogProfile patterns
  • Per-bus bandwidth from NCCL logs
  • CEL node health checks while workloads run
  • Per-node failure reporting with a reason
  • Topology-aware grouping and adaptive fault isolation
  • Checkpoint restart for training jobs
  • Optional spec.gangScheduler for gang-aware placement
  • WorkloadRun for ad-hoc training, NCCL, or custom workloads
  • The nvcrectl CLI for setup, render, run, report, and cleanup

What v0.4.0 actually runs

The first-certification catalog still has eight categories. The v0.4.0 release notes are explicit: nothing changed in the catalog, the controllers, or the CRD schemas. You can list the categories with kubectl nvcre certification list-categories.

Category What it does Scope notes
communication/nccl-all-reduce NCCL all-reduce performance Across all target nodes
communication/nccl-all-gather NCCL all-gather performance Across all target nodes
communication/nccl-alltoall NCCL all-to-all performance Across all target nodes
communication/nccl-loopback Single-node NCCL loopback One Job per node
communication/nccl-loopback-nvswitch Single-node NVSwitch loopback One Job per node
diagnostics/dcgm-level4 Deep DCGM diagnostic Needs standalone DCGM
training/nemotron5-8b Megatron-LM Nemotron 5 8B pretraining Min 4 GPUs; 8 on A100 (TP=8)
training/nemotron5-56b Megatron-LM Nemotron 5 56B pretraining Min 32 GPUs

Platform detection covers AWS, GCP, Azure, OCI, nscale, TogetherAI, Mistral, Forge, and on-prem. GPU architecture detection covers GB200, GB300, H100, H200, B200, A100, L40S, and L40. NVCRE tunes workloads from the nvidia.com/gpu.product label and the Node providerID. On-prem is the fallback when providerID is empty. On-prem GB200/GB300 still get the override from v0.3.0: arm64 and GPU-present taint tolerations, portable InfiniBand NCCL env without HCA pinning, and a NIC resource request that is auto-detected when exactly one candidate (rdma/* or nvidia.com/mlnxnics) is allocatable at the resolved mlnxPerNode count on every target node. Set nicResourceName when detection is ambiguous, or for offline nvcrectl certification render without --dry-run. Nodes with a metal3:// providerID detect as Mistral, not on-prem; pass --platform onprem on render if you need the generic override.

How certifications compose

The APIs compose the way Deployment, ReplicaSet, and Pod do. From the README: 

Certification ──one Workflow per catalog category──▶ Workflow
WorkloadRun   ──one Workflow from inline spec──────▶ Workflow
                                                     │
                                                     ▼
                                                    Job
                                                     │
                                                     ▼
                                      TrainJob (Kubeflow Trainer adapter)
                                                     │
                              ┌──────────────────────┴──────────────────────┐
                              ▼                                             ▼
                    GoodputMeasurement                          BandwidthMeasurement

A Certification creates one Workflow per catalog category. A WorkloadRun bypasses the catalog: it creates one Workflow directly from an inline workload spec. That is what nvcrectl workloadrun run uses for ad-hoc work. Each Workflow creates a Job. The Job creates the workload through an adapter, for example a Kubeflow Trainer TrainJob. Measurement resources parse pod logs with LogProfile regex patterns and compute goodput and bandwidth.

While those workloads run, CEL expressions watch node health. When a node fails, the certification result records it with a reason. The first-certification guide names three: WorkloadFailed (the workload exited badly), ThresholdViolation (a performance threshold was missed), and HardwareFailureDetected (the node health monitor fired mid-run).

Gang scheduling

Distributed workloads can deadlock under the default scheduler when only some of their pods fit: the placed pods hold GPUs while waiting for peers that never arrive. Optional spec.gangScheduler on Certification opts every category’s resolved TrainingRuntime pod templates into a gang-aware scheduler such as KAI Scheduler. The scheduler holds the pods until the full gang can be placed.

schedulerName is required. queue is optional and defaults to default-queue. queueLabelKey is optional and defaults to kai.scheduler/queue. The rewrite is certification-wide: after catalog and platform overrides resolve, it injects the scheduler name into every pod template and writes the queue value under that label key, including when a catalog entry hardcodes default-scheduler. 

apiVersion: nvcre.nvidia.com/v1alpha1
kind: Certification
metadata:
  name: gang-scheduled-cert
spec:
  target:
    nodeSelector:
      nvidia.com/gpu.product: NVIDIA-GB200
  enableMNNVL: true
  gangScheduler:
    schedulerName: kai-scheduler   # required
    queue: high-priority           # optional; defaults to "default-queue"
    # queueLabelKey: kai.scheduler/queue   # optional; this is the default
  categories:
    - domain: communication
      variant: nccl-all-reduce
    - domain: training
      variant: nemotron5-8b

On NVIDIA Run:ai, name that scheduler and its queue label, and set queue to an existing Run:ai queue — the default default-queue is not a real Run:ai queue: 

  gangScheduler:
    schedulerName: runai-scheduler
    queueLabelKey: runai/queue
    queue: team-a   # must name an existing Run:ai queue

nvcrectl certification render applies the same rewrite, so the rendered manifests show what the controller will create. Full detail is in the certify-a-cluster guide.

Air-gapped and mirrored installs

The controller itself needs no outbound network at runtime: catalog entries are compile-time embedded. Workloads and install still pull images and charts unless you point them at a mirror.

nvcrectl setup init can pull both Helm charts from a registry the cluster can reach: 

kubectl nvcre setup init \
  --chart-ref oci://registry.example.com/mirror/cluster-readiness-engine \
  --trainer-chart-ref oci://registry.example.com/mirror/kubeflow-trainer \
  --image registry.example.com/mirror/manager:v0.4.0

--chart-ref is used for the release install and for CRD extraction (helm show crds). The mirror must still host the NVCRE chart at this CLI version and Kubeflow Trainer at 2.2.1. Authenticate a non-GHCR mirror with helm registry login before init; --image-pull-secret is scoped to ghcr.io.

Catalog workloads can override the container image. Set image on the Certification spec, or per category under categories[].options (per-category wins). The override replaces the trainer image, the primary workload container, and init containers whose image matched the primary before the override (fix-ssh-permissions, megatron-clone). Distinct inits such as GCP’s tcpxo-daemon keep their catalog image. On AWS H100 and GB200, the platform override already lands NCCL workers on an nccl-tests image that ships the EFA OFI plugin; replacing that image means you own the plugin.

Multi-node MPI workers install openssh-server with apt-get unless /usr/sbin/sshd is already executable. Prebake sshd into the workload image for air-gapped clusters; the install then no-ops. Loopback NCCL categories are single-node and have no sshd bootstrap. AWS H100/GB200 (nccl-tests) and AWS GB300 (command replacement) already skip the install.

Training categories resolve Megatron-LM at pod start: an existing workspace at /mnt/workspace/megatron-lm, then source shipped in the image at /opt/megatron-lm, then a clone. The entry-defined default is https://github.com/NVIDIA/Megatron-LM.git, branch core_v0.15.2. For an internal Git mirror, set sourceRepo on the spec or per category (https:// or ssh:// only). Baking the pinned checkout into the image is the documented first choice when workers have no GitHub egress. 

spec:
  sourceRepo: https://git.example.com/mirrors/Megatron-LM.git

Evidence, not repair

NVCRE stops at evidence. It reports failed nodes. It does not cordon, taint, drain, or repair them. Quarantine is your platform’s job. Because cordoned nodes are skipped on later runs, kubectl uncordon is what brings a repaired node back into the next certification.

The README is also clear about non-goals. NVCRE is not:

  • A continuous monitoring system. It watches nodes only while its workloads run.
  • A general workload scheduler or production training platform.
  • A benchmark leaderboard. Measurements exist to find faults, not to rank hardware.

How to run it

The steps below follow the official README quickstart and Your first certification. Plan for roughly 30 to 60 minutes; most of that is the workload.

Prerequisites

Requirement Notes
NVIDIA GPU Operator NVCRE does not install it. Every target node needs the same nvidia.com/gpu.product label.
kubectl + helm Setup needs permission to create CRDs, cluster roles, and namespaces.
Prometheus Operator CRDs Default chart creates a ServiceMonitor for monitoring.coreos.com/v1. Or set metrics.serviceMonitor.enabled=false.
GB200 / GB300 NVIDIA DRA driver for ComputeDomain resources.
diagnostics/dcgm-level4 Standalone DCGM: patch ClusterPolicy with spec.dcgm.enabled: true.
Training categories Worker egress to github.com unless you bake Megatron-LM into the image, pre-seed the workspace PVC, or set sourceRepo.

Enable standalone DCGM when you need the level-4 diagnostic:

kubectl patch clusterpolicy cluster-policy --type=merge \
  -p '{"spec":{"dcgm":{"enabled":true}}}'

1. Install the CLI

v0.4.0 artifacts are signed with Sigstore and carry SLSA provenance. Preferred path: download the installer with its Sigstore bundle, verify with cosign, then run it pinned to the tag. Digests and exact cosign identity strings live on the v0.4.0 release. 

REL=https://github.com/NVIDIA/cluster-readiness-engine/releases/download/v0.4.0

curl -fsSLO "${REL}/installer"
curl -fsSLO "${REL}/installer.sigstore.json"

cosign verify-blob-attestation \
  --bundle installer.sigstore.json \
  --type https://slsa.dev/provenance/v1 \
  --certificate-identity "https://github.com/NVIDIA/cluster-readiness-engine/.github/workflows/attest.yml@refs/tags/v0.4.0" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  installer

bash installer -v v0.4.0

Piping releases/latest or a pin-by-tag installer into bash still works, but it is weaker: the script runs before anything has checked the script itself. TLS proves you reached GitHub; it does not prove the asset was untampered. 

# weaker: newest stable, no local cosign check of the installer itself
curl -fsSL https://github.com/NVIDIA/cluster-readiness-engine/releases/latest/download/installer | bash

# weaker: pin by tag, still pipes into bash
curl -fsSL https://github.com/NVIDIA/cluster-readiness-engine/releases/download/v0.4.0/installer | bash -s -- -v v0.4.0

The installer puts nvcrectl on your $PATH and creates a kubectl-nvcre symlink, so both nvcrectl and kubectl nvcre work. From this release, the installer also verifies each binary against that release’s Sigstore bundle before installing it (unless you pass --skip-verify). 

nvcrectl --version
kubectl nvcre --version

2. Preflight the cluster

kubectl nvcre cluster info
kubectl nvcre setup status

cluster info shows the detected platform, GPU product, ready node count, and topology labels when present. setup status tells you what is still missing. Install the GPU Operator yourself if labels are absent.

3. Install NVCRE

kubectl nvcre setup init

That installs Kubeflow Trainer 2.2.1, the NVCRE CRDs, the controller, and the built-in LogProfiles. Confirm with kubectl nvcre setup status.

Prefer Helm and want an explicit pin to this release’s chart digest. The v0.4.0 signature covers digest sha256:f55f49639834922ce4721b3905b65ce5706c0f0276c2d1c5babc77103c0cf01f at ghcr.io/nvidia/cluster-readiness-engine. The version tag is mutable, so verify and install the same digest: 

CHART=ghcr.io/nvidia/cluster-readiness-engine
DIGEST=sha256:f55f49639834922ce4721b3905b65ce5706c0f0276c2d1c5babc77103c0cf01f

cosign verify \
  --certificate-identity "https://github.com/NVIDIA/cluster-readiness-engine/.github/workflows/attest.yml@refs/tags/v0.4.0" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  "${CHART}@${DIGEST}"

helm pull "oci://${CHART}@${DIGEST}"
helm install nvcre ./cluster-readiness-engine@${DIGEST/:/-}.tgz \
  --namespace nvcre --create-namespace

helm install --version v0.4.0 resolves the tag at install time, which is not provably the digest you verified. helm install --verify looks for a PGP .prov file; this project publishes none.

The controller image is ghcr.io/nvidia/cluster-readiness-engine/manager:v0.4.0. This release signed these exact digests; pin the index rather than the tag:

To require that same signature and SLSA provenance at admit time, v0.4.0 ships two samples under config/samples/policy/: a Kyverno ImageValidatingPolicy and a Sigstore policy-controller ClusterImagePolicy. Both check the controller image before a Pod is admitted. From this tag, the attest self-test is gated to main, and attest.yml refuses allow_untagged on a release tag. The signed THIRD_PARTY_NOTICES.md asset matches the modules compiled into nvcrectl.

Setup next to an existing JobSet

nvcrectl setup init and setup reset now coexist with an existing JobSet installation.

setup init detects who owns the JobSet CRD before it touches Kubeflow Trainer. A verified external JobSet controller is reused: Trainer installs without the bundled one. A retained CRD with no controller gets the bundled controller without a schema refresh. Anything ambiguous stops before Helm mutation and prints the manual Trainer path with --skip-phases=deps.

setup reset keeps the shared JobSet CRD in every ownership mode, so JobSets that belong to other workloads survive. If Trainer uninstall fails, reset stops and exits non-zero instead of continuing into CRD cleanup. --skip-phases=helm is honored on both init and reset.

Breaking: both commands reject unknown --skip-phases values. init accepts deps and helm. reset accepts cr, helm, and deps. A script that passed any other name used to be ignored; it now exits with an error that names the accepted phases.

4. Certify one category

Start with communication/nccl-all-reduce. It works on any node count and finishes in minutes on a healthy cluster: 

kubectl nvcre certification run \
  --category communication/nccl-all-reduce \
  --wait

The CLI creates a namespace named nvcrectl-<timestamp> and a Certification in it. Note both names from the output. With --wait, it prints status updates and then the report.

5. Print the report again

kubectl nvcre certification report <name> -n <namespace>

The report command defaults to the default namespace. The run created its own, so leave out -n and you find nothing. That is the common first-day mistake called out in the guide.

On an execution failure, the failed-group section can include a captured log excerpt from one selected workload pod (pod, node, exit code, termination reason). JSON reports put the same data under categories[].failedGroups[].failureLog when the Job still exists. The field is absent if the failed Job was deleted before the report was generated.

The sample report in NVIDIA’s README is example output for an aws / gb300 / 16-node run, not a cluster I operated:

Ad-hoc WorkloadRun

For a single custom run without the catalog, write a WorkloadRun YAML. This is the README’s NCCL all-reduce example: 

# nccl-all-reduce.yaml
apiVersion: nvcre.nvidia.com/v1alpha1
kind: WorkloadRun
metadata:
  name: nccl-all-reduce
spec:
  image: nvcr.io/nvidia/pytorch:26.01-py3
  numNodes: 4
  framework:
    mpi:
      binary: /usr/local/bin/all_reduce_perf_mpi
      mpirunPath: /usr/local/mpi/bin/mpirun
      args: ["-b", "8", "-e", "32G", "-f", "2", "-n", "100"]
  bandwidthMeasurement:
    logProfileRef: nccl-bandwidth
    testType: all_reduce

numNodes is the node count per job group, not the cluster total. On a 16-node cluster, numNodes: 4 produces four 4-node jobs. 

kubectl nvcre workloadrun run nccl-all-reduce.yaml --wait

The same NCCL WorkloadRun, plus a multi-category Certification, also live as runnable files under examples/.

Cleanup

kubectl delete namespace <namespace>
kubectl nvcre setup reset

setup reset also removes Kubeflow Trainer. Pass --skip-phases=deps to keep it. The shared JobSet CRD stays in every ownership mode. If Trainer uninstall fails, reset stops and exits non-zero instead of continuing into CRD cleanup.
