Contributing to NVIDIA Cluster Readiness Engine

2 September 2026 · Anpoo Sivanadi

Two draft pull requests against an Apache-2.0 Go Kubernetes controller, opened issue-first and still waiting on maintainer acknowledgment.

I’m a Staff Software Engineer. Outside of day job work, I look for open source projects where the contribution surface is concrete: a named issue, a clear acceptance shape, and a path I can verify on a laptop without inventing a story about hardware I don’t have.

That is how I ended up in NVIDIA/cluster-readiness-engine (NVCRE), a Kubernetes controller that certifies GPU clusters. The project is Apache-2.0 and written in Go. My fork is asivanadi0/cluster-readiness-engine.

This note is a status report, not a victory lap. Nothing below is merged. Maintainers have not replied on the issues I commented on. NVIDIA CI has not run on either pull request. The drafts stay drafts until that changes.

Issue-first, not PR-first

I avoided claiming work that was already spoken for. Issue #140 was already assigned to kaynetu, so I left it alone.

I focused on two open, unassigned issues authored by mchmarny. Both sit under epic #262. I commented on each one before opening a pull request, and said I would wait for acknowledgment before treating the work as mine to land.

Issue #279 — Bring Makefile and workflow tool pins under automated updates

Phase 0 of the epic. Depends on #264. Sized S. Still open and unassigned when I commented.

My comment proposed a tools.go / gomod Dependabot path: move pinned Go-install tool versions into the module graph so the existing Dependabot gomod ecosystem can age them, instead of leaving version strings only in the Makefile. I said I would wait for ack before opening a PR. I opened a draft anyway so the change is inspectable; it is still labeled draft and still closes #279 only if maintainers want that direction.

Issue #274 — Workflow policy regression tests

Phase 4 of the epic. Depends on #265 and #270. Sized M. Still open and unassigned when I commented.

Four invariants were still outstanding on the issue:

  • attest.yml is the sole signer
  • id-token: write only on signing jobs
  • every uses: is a SHA
  • NVCRECTL_PLATFORMS matches expected-asset lists

My comment took those four remaining invariants as mutation tests. That is the scope of the second draft PR.

Draft PR #294: Makefile Go tool pins via tools.go

PR #294 — build: bring Makefile Go tool pins under Dependabot via tools.go. Draft, open, head on asivanadi0, base NVIDIA main. Intended to close #279. Diff: +862 / −35 across 7 files.

Files touched:

  • tools/tools.go
  • Makefile
  • go.mod and go.sum
  • .github/dependabot.yml
  • comments on attest.yml and release.yml

Behavior change, limited to build tooling: six Makefile go install tool versions now live in go.mod through tools.go and the Go tool directive. Dependabot keeps using its existing gomod ecosystem and cooldown. The Makefile reads versions with gomodver. GOTOOLCHAIN is pinned for CLI installs.

Cosign, crane, syft, yq, kind, tilt, and kwok stay deliberately manual, with that choice documented in the PR. This is not a runtime or product-code change.

Checks so far: DCO SUCCESS, CodeRabbit SUCCESS. NVIDIA CI has not run; copy-pr-bot is waiting on /ok to test.

Draft PR #295: release workflow policy invariants

PR #295 — test: enforce release workflow policy invariants (#274). Draft, open. Diff: +502 / −2 across 2 files.

Files touched:

  • test/releasepolicy/workflow_policy_test.go
  • .github/workflows/release.yml

The new tests treat the four remaining #274 invariants as mutation tests: if a future change breaks the policy, the suite should fail before the workflow ships that way. Same check status as #294: DCO SUCCESS, CodeRabbit SUCCESS, no NVIDIA CI yet for the same /ok to test gate.

What I could verify locally

On the machine I used for this work I cloned upstream main at 8120b15, with Go 1.27. make test, make lint, and make build passed.

That is the limit of the local story. There was no Docker, so UAT was skipped. There was no NVIDIA GPU, so I did not run a full Kubernetes GPU certification path. I am not claiming a cluster run, NCCL results, or any product validation beyond those Makefile targets.

What this is not

A Kubernetes Slack post was drafted. I am not claiming it was posted.

There are no maintainer quotes here because there are none yet. No review approvals. No merge. No NVIDIA CI pass or fail to report. The drafts are not merge-ready.

Next

Waiting on maintainer acknowledgment on #279 and #274, then /ok to test, then real CI and human review. Until that sequence happens, both pull requests stay drafts.
