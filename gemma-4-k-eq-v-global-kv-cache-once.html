Gemma 4 Stores Its Global KV Cache Twice: Measuring the 37.5% That Serving Engines Leave Behind

22 November 2026 · Anpoo Sivanadi

The Gemma 4 technical report makes a specific memory claim. In the global attention layers of every model except E2B and E4B, keys are reused as values, and with p-RoPE at p = 0.25 that "effectively" reduces the global KV cache by 37.5%. I assumed the open engines collected that saving. They do not. A preprint posted this week, Storing the Gemma 4 K=V Cache Once by Kushagra Bainsla of San José State University, reads the KV code of vLLM, SGLang, TensorRT-LLM and Hugging Face transformers and reports that each one writes a full key and a full value for these layers: 1,024 values per KV head and token where 640 would do.

The paper then builds the 640-value layout in vLLM without touching an attention kernel, and measures it on A100s. The author also opened vLLM RFC #68778 on November 19 to propose it upstream. Figures below come from the paper, the RFC, the Gemma 4 report and config.json; where I extend them, I say so.

1. What the config actually says

The config.json for gemma-4-31B-it has 60 layers: 50 sliding_attention and 10 full_attention. Sliding layers have 16 KV heads of dimension 256 and a 1,024-token window. Global layers have 4 KV heads (num_global_key_value_heads) of dimension 512 (global_head_dim), partial_rotary_factor 0.25, and attention_k_eq_v: true. Max position embeddings are 262,144. The same flag is set in the 26B-A4B config (2 global KV heads) and the 12B config (1 global KV head), and is false for E4B.

The paper spells out what the flag means. A global layer has no value projection. The value is the RMS-normalized key projection, with no learned scale. The key is that value multiplied elementwise by the key-norm weight, then rotated by RoPE on 128 of the 512 dimensions (dimensions 0 to 63 and 256 to 319). On the other 384 dimensions RoPE is the identity, so the key there is just a fixed weight times the value.

The RFC describes vLLM main today: gemma4.py loads k_proj into both the K and V shards of qkv_proj, computes V from the duplicate, and passes separate K and V tensors to attention, so the cache holds both. A separate open PR, #41944, removes the duplicate V projection weights, but the cache still stores two tensors.

2. The 640-value row

The trick is to store, per KV head and token, the 128 rotated key values, then the 384 unrotated value dimensions, then the 128 rotated value dimensions. That is 640 values. The first 512 are read as the key cache and the last 512 (starting at offset 128) as the value cache, as two strided views of the same buffer. Any kernel that accepts separate key and value tensors with explicit strides reads them unchanged.

Two small transforms make the math work. The fixed key-norm weight on the unrotated dimensions is folded into the query, so the score against the stored value equals the score against the real key. The value view comes out in a permuted dimension order, and a fixed permutation restores it before the output projection. In real arithmetic this is exact. In 16-bit arithmetic it is not bit-exact against stock, because the roundings and summation order change.

Why not 512 values and a 50% saving? Because the rotation angle differs per cached token, the rotated key cannot be folded into the query once. A 512-value row needs a new kernel that rotates while it reads. The author kept 128 extra values to avoid writing one.

The page allocator takes a cut. vLLM requires one page size in bytes across layer groups. A stock global page and a sliding page are both 262,144 bytes. The largest compact global page that fits is a 48-token block of 245,760 bytes, padded to 262,144, so 6.25% is unused. Global bytes per token per layer drop from 8,192 to 5,461: a factor of 1.5 instead of the ideal 1.6. An open vLLM proposal for unequal page sizes (#64307) could remove the padding.

3. What it measured

The prototype runs on vLLM 0.33.0rc1.dev229 with the Triton attention backend, which vLLM forces for Gemma 4 on A100 because FlashAttention-4 is not available there. The model is the 16-bit 31B checkpoint with a 16-bit KV cache and a fixed 15 GiB pool (6,144 blocks) on one A100 SXM 80GB, since the 62.6 GB of weights leave about that much. Kernels are unchanged; the patches are Python wrappers and module hooks on the 10 global layers.

Correctness: the compact engine and an emulation of the same arithmetic on the stock cache gave bit-identical outputs on all 432 prompts (400 GSM8K problems and 32 needle prompts of 7.7K tokens). Against the stock engine, 2 of 432 final answers changed, both toward correct, and generated text differed in 88 items. The author calls that "no break found", not proof of equal quality; no accuracy test reaches the lengths where the saving matters.

Memory: steady decode KV per request fell from 1,349 to 1,008 blocks at 32K tokens (3.29 to 2.46 GiB, 1.338x) and from 2,373 to 1,690 blocks at 64K (5.79 to 4.13 GiB, 1.404x). Prefill peaks fell less, 1.15x and 1.23x, because the prefill reservation still includes up to 321 blocks per sliding group.

At 32K the pool held 4 compact requests instead of 3, and decode rose from 56.0 to 69.7 tokens/s (1.24x). At 64K both layouts held 2 requests and the compact build was 4% slower; the third request was short 181 blocks. In eager mode the compact step was 8.7% slower at 32K and 4.3% slower at 64K at equal batch, mostly from about 110 extra small kernels per step. In an exploratory full-CUDA-graph run the step costs were 50.52 ms versus 50.73 ms, but that run failed its own output check on one of three prompts, so the paper marks it invalid.

The per-step speed bound is worth remembering. At 3 requests of 32K, a decode step reads about 62 GB of weights and 10.6 GB of KV; the compact cache removes about 2.7 GB of 73 GB, so even a perfectly bandwidth-bound step gains about 4%. Any real gain comes from fitting more requests.

4. In a disaggregated decode node

The section most useful for prefill/decode splits uses two A100s: prefill on one, decode on the other with NIXL transfer and a 64 GiB CPU offload tier, and a backlog that kept the decode pool full in at least 99.6% of work steps. The pinned NIXL connector could not register the compact cache until a small byte-view patch; the author believes vLLM main later fixed this generally.

With 16K-token median prompts and 2,048-token outputs, the compact decode engine ran 1.376x the stock decode tokens per step, repeated to 0.06% on another host. With 8K prompts it was 1.237x. A discrete-step model of the vLLM block pool, frozen before each run, predicted 1.364x and 1.229x. Eager decode throughput rose 1.30x and 1.11x. The gain shrinks with prompt length because sliding-layer memory is fixed by the 1,024-token window.

5. The limits

One model, one vLLM build, Triton on A100, 16-bit cache only. At the default FP8 KV scale of 1.0 the compact row fails the author's attention-error bound, so the 1.34x to 1.40x does not yet stack with an FP8 cache. Tied per-row FP8 scales came in at 1.06x the attention error of vLLM's per-token-head FP8 cache, with no engine-level test. Prefix caching, tensor parallelism, speculative decoding and more than 16 concurrent sequences were not tested. The decode-node bands passed only after being widened by 1%, and throughput ratios are single runs against a 2.7% stock A/A spread.

My take

By my arithmetic from the config, a stock 31B request holds 81,920 bytes of global KV per token (10 layers x 4 heads x 1,024 values x 2 bytes), plus a fixed 800 MiB of sliding-window KV. At the full 262,144-token context that is 20 GiB of global KV per request; the padded 640-value layout brings it to about 13.3 GiB. That matches the RFC's own table at 128K (10.78 GiB today versus 7.03 GiB ideal). On paper, before activations and runtime overhead, that is the difference between one full-length request fitting next to 62.6 GB of 16-bit weights on an 80 GB card or not.

I would not flip anything in production yet. The RFC has no maintainer response so far, the prototype is eager-mode Triton on Ampere, and FP8 KV caches, the common setting on Hopper and Blackwell, are exactly where this has not been shown to stack. What I would do now is count. If you serve Gemma 4 31B or 26B-A4B at long context, compute your global KV share per request; if it dominates, follow #68778 and #64307. I wrote about trading KV bits for capacity in BitDecoding-FP4; this is the rarer case where the bytes were redundant all along and the only cost is a layout.
