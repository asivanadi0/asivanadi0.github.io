A Shared L2 KV Cache Over EFA: Reading AWS's Distributed KV Caching Numbers

19 November 2026 · Anpoo Sivanadi

On November 18 AWS announced general availability of distributed KV caching on ElastiCache for Valkey. The idea is not new. LMCache, Mooncake and NIXL-based setups have shown for a while that a KV cache can live outside the GPU server. What is new is a managed tier with published latency, a published failure test and a limits page that is unusually blunt about what the cache will not do. I read the announcement, the service docs, the limits page and the LMCache Valkey adapter docs. This is what I took away. Arithmetic marked as mine is mine; every other number comes from those pages.

1. The tier model

AWS describes three tiers. L0 is GPU memory, which it puts at up to 288 GB of HBM3e per GPU, shared between weights and in-flight requests. L1 is host DRAM and local NVMe, reached through an offload library such as LMCache, and private to one server. L2 is the new shared tier: a Valkey cluster in the same Availability Zone that every GPU host can read.

The lookup order is L0, then L1, then L2 only on a miss. On a write, the connector pushes new KV state to L2 so any server can reuse it later. The engine side does not change. vLLM and SGLang talk to an LMCache server running on each GPU host, and LMCache talks to Valkey.

One discrepancy worth knowing: the blog lists TensorRT-LLM next to vLLM and SGLang, but the how-it-works page says TensorRT-LLM support is in the LMCache development branch and not in a stable LMCache release yet. If you run TensorRT-LLM, plan on a dev build or wait.

2. The hardware underneath

Everything runs on one node type, cache.i8ge.48xlarge, an EFA-enabled node based on EC2 I8ge, with Valkey 9.1 or later. The storage engine is the new valkey-large-object module, which adds a BLOB.* data type. Hot blocks sit in DRAM, colder blocks tier down to local NVMe automatically, and transfers go over RDMA on EFA at up to 220 Gbps per node.

The limits page gives the sizing facts:

Limit Value
Max value size (BLOB.*, SET, GET) 512 MiB
Max large object cached in DRAM 256 MiB
NVMe instance storage per node 120 TB
NVMe allocation granularity object length rounded up to 4 KiB

For scale, the AWS benchmark baseline gave each GPU server about 150 GB of L0 and 205 GB of L1. My arithmetic: one cache node's 120 TB of NVMe is roughly 340 times that combined local footprint. Capacity is not the constraint here. Bandwidth and hit rate are.

3. The latency table, translated

AWS published P50 and P99 for one node:

Operation P50 P99
Get one 8 MB object 477 µs 950 µs
Set one 8 MB object 881 µs 1,010 µs
Get 1 GB (128 x 8 MB) 41.7 ms 42.1 ms
Set 1 GB (128 x 8 MB) 44.6 ms 49.4 ms

My arithmetic: 1 GB in 41.7 ms is about 24 GB/s, or roughly 192 Gbps. That is about 87% of the 220 Gbps line rate, so the batched path is close to wire speed. A single 8 MB get works out to about 17 GB/s at P50, and the P99 roughly doubles it. The tight P50 to P99 gap on the 1 GB batch (41.7 vs 42.1 ms) is the number I like most. Batched KV loads are what a long prefix restore looks like, and a flat tail there is what keeps TTFT predictable.

What the table does not say: how many clients were reading at once, whether the objects were DRAM-resident or on NVMe, and how the numbers change when several GPU hosts hit the same node. A single node at 220 Gbps is shared by every host that reads from it. If eight servers restore long prefixes at the same moment, they split that pipe.

4. Where it pays off and where it does not

AWS tested 2 to 6 P6 servers with 8 GPUs each running vLLM, five 2026 models with sparse and hybrid attention from 250B to 1.6T parameters, against coding-agent traces, an agentic assistant trace and long-context Q&A (LooGLE and L-Eval). The comparison runs added one cache node.

  • Long-context Q&A: each server handled 2x the requests per second within an SLO of p90 TTFT under 5 s and p90 TPOT under 50 ms. AWS says that cut cost per million output tokens by 40% after paying for the cache node.
  • Coding agents and assistants: 23% higher peak token throughput per server, and up to 1.98x (coding) and 1.61x (assistant) throughput at the same load under a 30 s p90 TTFT SLO.
  • TTFT per cache hit: 55% to 93% reduction across eight models (two full-attention, three sparse, three hybrid).

The part I would act on is the cutover point: the prompt length above which loading from L2 is faster than recomputing. Every model they tested cut over below 10K tokens. Sparse models cut over under 512 tokens, because they store little KV per token while prefill stays expensive. Hybrid models cut over between 1,000 and 7,600 tokens, because their fixed-size recurrent state dominates the payload at short lengths; their gain grows to 84% past 100K tokens and up to 93% near 1M. AWS's advice is to find the cutover for your model and only cache prompts above it. I agree, and I would add that the cutover moves with load on the cache node, so measure it at peak, not idle.

AWS also lists where it helps little: deployments whose KV fits comfortably in HBM, single-shot calls with no reuse (classification, translation, moderation), and long outputs from short prompts.

5. The failure test is the real argument

Prefix-aware routing already gets you a lot of reuse when the fleet is stable. The shared tier earns its keep when the fleet is not stable. AWS stopped one server in a two-server setup and brought it back:

  • With the cache, the surviving server held p90 TTFT to 34.7 s over the first 300 s, 43% lower than without it, while completing 1.48x the requests.
  • After the server returned, the system was back to its original throughput and TTFT within 60 s. Without the cache it took up to 600 s, and queued requests still held p90 TTFT at 12.1 s.

That 60 s vs 600 s recovery is the number I would show to anyone running autoscaled inference. A new or restarted replica that can hydrate from L2 does not start cold.

6. The fine print on the limits page

This is a cache in the strict sense, and the docs say so plainly:

  1. No persistence. No snapshots, backups, restore or replication. A node reboot, replacement, patch or failure removes all objects on that node. Service updates and engine upgrades empty the cache. LMCache treats a failed read as a miss and the engine recomputes.
  2. Single AZ, no replicas. Replicas per shard is fixed at 0 and Multi-AZ cannot be turned on. Your GPU fleet and the cache must sit in the same AZ.
  3. Fixed size. You cannot add or remove shards, rebalance slots or autoscale, because large-object keys cannot move between shards. To resize, you create a new cluster and reload. AWS says to size shard count on the larger of total object storage and peak read bandwidth.
  4. Transport matters. The LMCache transport default is tcp, plain SET/GET over TLS, which the ElastiCache docs describe as for functional tests; those values live in node memory, not NVMe. RDMA ("transport": "rdma") needs valkey-glide-sync 2.6.0 built with RDMA support and libfabric 2.4 or later on the client. In RDMA mode request_timeout does not bound a transfer, because a posted write cannot be called off, and num_workers is your in-flight transfer count.
  5. Encryption is mandatory. Transit encryption is set to required and at-rest encryption is always on.
  6. Pricing. Standard per-node-hour pricing for cache.i8ge.48xlarge, no charge for same-AZ data transfer to GPU hosts, reserved nodes available. The announcement does not quote a price, so the 40% cost figure depends on a node price you have to look up yourself.

7. What I would do before buying

AWS shipped KVTrace, which records the KV cache events vLLM and SGLang already publish (--kv-events-config over ZMQ in vLLM) and simulates hit rate and savings at different cache sizes offline. The limits page notes it models only node DRAM, so its hit rate is a lower bound. My checklist:

  1. Run KVTrace on every replica for a full traffic cycle, including the hours your users come back after a break.
  2. Find the cutover length for each model you serve and set a minimum prefix length for L2 writes.
  3. Load-test RDMA transport with all hosts restoring at once and record per-host bandwidth, not just the single-client table.
  4. Kill a replica under load and compare time-to-baseline with and without L2. That is the test the announcement leads with, and it should reproduce.
  5. Decide what happens during cache maintenance windows, since the cache comes back empty.
  6. Pin LMCache, valkey-glide-sync and libfabric versions together; the RDMA path depends on all three.
