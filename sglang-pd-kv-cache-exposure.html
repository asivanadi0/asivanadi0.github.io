When Is a KV Cache Page Actually Free? Reading the SGLang and Cloudflare PD Disclosure

27 October 2026 · Anpoo Sivanadi

If you run prefill/decode disaggregation, you have a distributed memory allocator whether you meant to build one or not. Yesterday two posts made that point in the most expensive way possible.

On October 26, SGLang published a coordinated disclosure and Cloudflare published its incident report. Between August 27 and September 9, 2026, GLM-5.3 on Workers AI (@cf/zai-org/glm-5.3) returned 155 responses that contained data from other customers' requests. Every one of them was a reply to a prompt longer than 681,280 tokens. Cloudflare says it found no evidence of deliberate exploitation, and no other Workers AI model was affected.

There are really two bugs here, and they share one question: when is a KV cache page safe to hand to the next request?

1. Bug one: a rejected request that still looked alive

Cloudflare served GLM-5.3 with a configured context window of 1,048,576 tokens. The prefill KV pool on those nodes only had room for 681,280 tokens. SGLang sizes that pool from whatever GPU memory is left after the weights load, and nothing forces it to agree with the context setting. Cloudflare says it knew about the mismatch and assumed the engine would error on anything it could not fit.

The engine did not error. When a prompt exceeded the pool, SGLang's scheduler marked it rejected and swapped the prompt for a one-token placeholder, so it could drain through normal batching. On a single node that works and the client gets an error. In disaggregated mode, both admission queues checked req.finished(), and a rejected request stored its rejection in to_finish, not finished_reason. So it reported itself as live.

Decode reserved pages for the full prompt length. Prefill ran a forward pass on the placeholder token, sent one page, and signaled completion. Decode then attended over every reserved page, and all but the first still held what earlier requests had left. KV pages are not zeroed between requests, which is normal across engines, so the client got a coherent HTTP 200 containing other users' content.

The engine fixes: #36988 retires aborted requests when their final prefill result is processed, and #38935, merged September 16, rejects them at the admission queues before any bootstrap, allocation or transfer state exists.

2. Bug two: a distributed use-after-free with the pointer sitting in a NIC queue

The second half of the SGLang post is the part I would hand to anyone building PD on any engine.

SGLang's KV transfer is push-based. Prefill writes chunks into decode's pre-reserved slots using one-sided RDMA WRITE through Mooncake, NIXL or MORI, overlapped with the prefill computation. If a request dies mid-transfer from a client disconnect, timeout, transport fault or prefill failure, older builds had decode return those slots to the allocator at abort time. Prefill could not recall a write it had already posted:

  • RDMA verbs have no call to cancel a single work request already posted to a queue pair.
  • Python cannot interrupt a blocking C++ transfer call such as Mooncake's batch_transfer_sync. If that call times out, its work requests remain posted with no completion accounting.
  • One-sided writes bypass the receiver's CPU, so decode gets no per-write signal to wait on.
  • The NIC places data per packet, so an interrupted write can still leave a partial prefix.

So the allocator could mark a slot free, hand it to request B, and then A's late write lands inside B's KV cache. Nothing logs an error. The SGLang team calls this a distributed use-after-free, which is exactly right. Pull designs do not escape it either, since a posted RDMA READ cannot be taken back.

The window scales with context length. A short prompt is in flight for milliseconds. A 128K to 1M token context keeps writes in flight for seconds to minutes. In their 2x H200 reproduction over Mooncake RDMA, with two prefill engines sharing one decode, a victim request counted correctly to 80 and then started emitting the aborted request's prompt text.

The SGLang post says default PD configurations were exposed to this race from the v0.4.x line until v0.5.21, or v0.5.22 for MORI. The leak is one-way, but in multi-tenant serving it is still data leakage.

3. The fix: hold the slot until the writer proves it is done

Decode cannot cancel prefill's writes, so it keeps the aborted request's slots reserved longer than those writes can land. The design condition in the post is:

T_hold > t_abort_propagation + t_remaining_chunks + t_in_flight_call

The pieces that make that hold true:

  • Abort notification to prefill (#27372). Decode sends ABORT to every prefill rank, which drops queued chunks for that room. That shrinks the remaining-chunks term to near zero.
  • Deferred release (#35049, NIXL port #35360). On abort, decode holds the KV slots, the request-pool row and the metadata buffer entry. Each prefill rank replies ABORT_ACK only when its outstanding count for that room drains to zero. Decode releases on the last ack or on a timeout, 30 seconds by default in #35049.
  • Hold on every failure kind (#41404) and a working ack fast path (#40645, #41402). A Cloudflare audit (#38961) found the ack often never arrived and some fault types never armed the hold.
  • Failed sends never count as drained (#43719 for Mooncake, in v0.5.22; #45973 for NIXL and MORI, slated for v0.5.23).
  • Generation-tagged acks (#37077, v0.5.22), so a reused room id cannot consume a stale ack.

Deferred release became the default in v0.5.21. The cost they report is small: across 21 runs on 2x H100 (1P1D Mooncake, 1,024 requests at concurrency 256), throughput deltas stayed within plus or minus 2% with every 95% confidence interval spanning zero.

4. What I would actually change in a PD deployment this week

My checklist, combining both posts' guidance:

  1. Compare KV pool size with context length on every prefill and decode node, from the engine's own startup log or metric, after any change to weights, quantization, parallelism, CUDA graph sizes or memory fraction. If the pool is smaller, lower the context length. This is the check Cloudflare says it did not enforce, and after the fix its GLM-5.3 prefill pool holds about 2.04 million tokens. Pool sizing belongs next to the parallelism choices I covered in my GLM-5.3 PCP/DCP post.
  2. Upgrade to v0.5.22 or later. There are no backports to older branches. Cut builds past #41128 to get the release metrics. Watch for mixed-version prefill and decode during rollout: mismatched ack formats make the handshake fail and every release falls back to the timeout.
  3. If you are stuck on v0.5.19 or v0.5.20, set SGLANG_DISAGGREGATION_DEFERRED_DECODE_KV_RELEASE=1 on both roles. On v0.5.20 also set SGLANG_MOONCAKE_MAX_TRANSFER_BATCH_INDICES and a release timeout of 60 to 120 seconds.
  4. Size the hold. If releases fall to the timeout, held capacity is roughly abort rate times T_hold times pages per request.
  5. Alert on sglang:decode_deferred_kv_release_total{outcome}. Healthy deployments release almost everything through drained. A rising timeout share means the ack path is broken.
  6. Turn on detection where it covers your model. --disaggregation-enable-kv-checksum (#39500) computes an Adler-32 on the GPU at prefill and checks it at decode before the request joins a batch. Cloudflare notes the checksum and --kv-canary do not yet cover every architecture, including GLM-5.3 and DeepSeek V4, so check your logs to confirm requests are actually being verified.
  7. Stop your proxy from creating aborts. Cloudflare changed its load balancer so a client disconnect no longer aborts mid-transfer: it keeps the prefill connection until prefill finishes and the decode connection until the first token. Also run a router that cancels both halves together.

5. The part that should bother everyone else

None of the mechanics in section 2 are unique to SGLang. Any engine that moves KV between nodes, memory tiers or pipeline stages with asynchronous DMA has to answer the same question, and "the allocator says free" is not the answer. SGLang's four closing rules are a good review checklist for any of them: never free a slot an async engine may still touch, hold until a positive drain signal or a bounded timeout, make every degradation lengthen the hold, and keep each fix small enough that its test proves one thing.

Cloudflare's longer-term direction is integrity at read time: tag each physical page with a value that changes on reallocation and check the request's expected tags before decode reads the cache. Its prototype cost under 1% in tests but was disabled for reliability issues. Zeroing pages on release is still a draft proposal (#46435). Until something like that ships in the engines we run, the controls are pool sizing, deferred release, and metrics that tell you whether the hold is actually working.

The lesson I am taking from Cloudflare's write-up is the testing gap. Its long-context tests checked status codes and throughput, not whether the output belonged to the right request. A canary test that plants a unique string in one tenant's prompt and greps for it in everyone else's output is cheap to add to any PD qualification run.
