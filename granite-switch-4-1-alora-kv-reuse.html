Granite Switch 4.1: Three Models' Worth of Jobs on One KV Cache

17 October 2026 · Anpoo Sivanadi

IBM shipped Granite Switch 4.1 this week in 8B and 30B sizes, Apache 2.0. The pitch is one endpoint that handles chat, a yes/no safety judge, a multiple-choice "decision" classifier, and speech-to-text. Plenty of stacks already do that with four deployments. What caught my attention is how this one does it with one checkpoint and, more importantly, one KV cache, and what that means for the prefill bill in an agent loop.

I spent the afternoon reading the model card, the composed config, and the design docs in the granite-switch repo. The idea is good. A few of the limits are the kind you only find by reading source, so I'll cover those too.

What's in the checkpoint

From the 30B model card, its BUILD.md, and config.json:

Item Granite Switch 4.1 30B
Base model granite-4.1-30b, dense decoder, 64 layers, hidden 4096, 32 query heads, 8 KV heads (GQA), 128K context
Adapters guardian-core (aLoRA, rank 16, attention projections only) and decision (aLoRA, rank 64, attention plus MLP)
Speech granite-speech-5.0-470m-turboctc, a 470M-parameter English CTC encoder
Parameters 28.87B base, 29.99B composed, +3.89%
Weights on disk about 60 GB in BF16
Serving Transformers, or vLLM through a plugin pinned to >=0.26.0, <0.28.0

The 8B has the same adapter and speech setup on an 8B base. There are also "preview" checkpoints at 3B, 8B, and 30B that pack the full Granite Libraries adapter set without audio.

So the memory story is simple. You pay for a 30B model plus about 1.1B of adapter weights and a small speech encoder, instead of a chat model, a separate guard model, and a separate ASR box.

Why the KV cache is shared

A normal LoRA changes the Q, K, and V projections for every token in the request. That means a KV block computed under adapter A isn't valid for adapter B or for the base model, and vLLM's prefix cache knows it: the LoRA name goes into the block hash. Switch adapters on the same 16K-token context and you prefill the whole thing again.

An activated LoRA (aLoRA, from IBM's NeurIPS 2025 paper) only applies its weights to tokens after an invocation point. Everything before that point runs on the frozen base weights, so its KV is bit-for-bit what the base model would have produced. The adapter reads it and adds its own tokens on top.

Granite Switch moves the selection inside the model. A control token like <|decision|> sits in the token stream, and a small "switch" layer, built from two single-head attention calls with no learned router, turns it into a per-token adapter index that every decoder layer reads. The repo's MultiSwitch doc spells out the consequence: vLLM hashes a block from its parent hash, its token IDs, and some extra keys like the LoRA name, and Granite Switch sets none of those extra keys. Two requests with the same token prefix share blocks, whichever adapter comes later. Since routing is computed from those same tokens, a reused block is always what recomputing would have given you.

That's the whole trick. It isn't a new cache. It's arranging things so the cache vLLM already has can do its job.

What that saves, roughly

IBM's repo shows a live race between an aLoRA and a standard LoRA version of the same model on the same hardware. Partway through, the aLoRA side had a 74% KV hit rate and 5 of 16 queries done, and the LoRA side had 29% and 1 of 16. The blog also says the 30B with four specialized adapters finished a five-step RAG workflow "much faster" than JEV-27B. Neither gives a hardware spec or wall-clock times, so I treat both as directional.

Here's my own back-of-envelope instead. The 30B base stores 2 × 64 layers × 8 KV heads × 128 dims × 2 bytes, which is 256 KiB of KV per token in BF16. A 16K-token RAG context is about 4 GiB of KV. Re-prefilling it costs roughly 2 × 29B × 16K ≈ 0.95 PFLOP for the weights alone, plus a few hundred TFLOP for attention at that length. On one H100 at realistic utilization that's a couple of seconds. If an agent step asks a guard question and two decision questions about the same context, a per-request LoRA setup pays that three extra times. With aLoRA, each question costs a few dozen new tokens of prefill plus one decode step. These are my estimates, not IBM's numbers, but the order of magnitude is what makes the design worth looking at.

The kernels matter as much as the cache

The other half is a new LoRA kernel path IBM calls SWITCH. vLLM's Punica path runs three launches per wrapped projection (base GEMM, shrink, expand) and sizes every adapter slot to the engine-wide max_lora_rank. SWITCH stacks the base weight and every adapter's A matrix into one GEMM, then runs one Triton kernel that applies each token's own B matrix in place, at that adapter's own rank.

Their numbers, on Granite 4.1 3B, 1× H100, BF16, batch 32, vLLM 0.22.1, 512-token prompts and 128 output tokens:

Adapter mix SWITCH vs Punica, decode
All rank 32, 1 adapter 1.21×
All rank 32, 12 adapters 1.38×
12 × rank 32 + 1 × rank 128 up to 2.5×
12 × rank 32 + 1 × rank 512 up to 5.9×

The rank-512 row is the one to remember. Adding one big adapter cut Punica from 2,521 to 493 tok/s, an 80% drop, because every request got computed at rank-512 width. SWITCH went from 3,472 to 2,753 tok/s, since only the tokens using that adapter paid for it. At 8B the gains shrink to 1.11–1.32× with balanced ranks and 1.26–1.99× with one rank-128 adapter.

There's a cost: with no adapter active, SWITCH runs about 5–10% slower than plain vLLM at 8B, because it runs as one CUDA graph while vLLM swaps to a no-LoRA graph. IBM says a two-graph version would close that. For a deployment where most traffic is plain chat, that idle tax is real and you should measure it.

What I'd check before running it

Don't turn on an FP8 KV cache. The switch layer pushes a -1e9 mask constant and memory keys scaled by 28 through the paged KV cache. Both blow past FP8 E4M3's maximum of about 448. The doc says --kv-cache-dtype fp8 would wreck routing and nothing currently rejects the flag. If your fleet sets FP8 KV by default, this checkpoint needs an exception.

There's a ceiling of 188 control tokens per request in BF16. The counting head's signal is 1/(1+n) stored in the KV dtype, and BF16 can't tell 189 from 190 apart. At 190 control tokens two adapter spans collide and tokens get routed to the wrong adapter with no error. The Conversation helper re-prefills before that point, but a client that posts token IDs straight to /v1/completions never goes through it. Long agent sessions that keep every turn's control token are the ones that can hit this.

Chat completions can quietly lose your cache hits. /v1/chat/completions re-renders the transcript on the server, and the template emits only the current turn's control token. The previous turn's token disappears, the prefix stops matching there, and everything after it gets prefilled again. To keep multi-turn reuse, the repo says to send token IDs to /v1/completions through its Conversation API. A falling cache-hit rate is the only symptom, so put it on a dashboard.

The vLLM pin is old. The card wants vLLM below 0.28, and vLLM 0.31 is already out. If you run a shared vLLM image across models, this one probably needs its own.

The speech path is a cascade, not a fused model. The ASR encoder isn't trained jointly with the LLM, outputs lowercase unpunctuated English, and a mistranscription feeds the guard and decision adapters as if it were what the user said. Fine for a demo, worth a test set before anything that matters.

The decision numbers are modest. The decision adapter scores 50.1 overall on the public Decision Index fast subset (1,068 rows), with Tools at 76.5 and Arts at 26.4, and local and hosted serving agree within about 0.6 points. IBM's case is that cheap specialist adapters beside one generalist beat a single big generalist on targeted tasks, and the shared cache is what makes stacking them cheap. That's plausible, but check it on your own labels.

Where this fits

Most agent stacks I see call a guard model, a router or classifier, and a main model over the same context, often as separate services that each prefill it again. Granite Switch is a clean, open example of collapsing those into one model whose cache key is just the tokens. The design generalizes. The specific checkpoint has sharp edges around KV dtype, control-token counts, and API choice that you only find by reading the docs closely.

If you try it, the cheapest experiment is IBM's aLoRA vs LoRA race notebook, then one of your own multi-step flows with vLLM's prefix-cache hit rate exported next to TTFT.
