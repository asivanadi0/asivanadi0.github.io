NVIDIA Snapshot Brings a 913 GB MoE Replica Back in 40 Seconds: Reading the Cold-Start Tables

15 November 2026 · Anpoo Sivanadi

Every time an inference deployment scales up, the new replica pays the same tax: start the engine, read the weights, allocate the KV cache, run torch.compile, autotune kernels, capture CUDA graphs. For a small model that's a couple of minutes. For an 8-GPU MoE it can be a quarter of an hour, during which the GPUs are allocated and serving nothing. That is why most teams I know keep idle replicas warm instead of scaling to zero.

NVIDIA's answer, published on Nov 10, is Snapshot, an open-source (ai-dynamo/snapshot) checkpoint and restore system for GPU pods on Kubernetes. It captures a fully initialized workload, including CPU and GPU memory, and restores it on another node with the same GPU model and driver. The process continues from where it was checkpointed, so weight loading, compilation and graph capture are skipped. The post came with full per-phase tables across vLLM, SGLang and TensorRT LLM, and two design partners, Crusoe and Saturn Cloud, published their own B300 runs the same day. I haven't run it yet; these are notes from the tables and the repo docs.

1. How it works

Snapshot is built on two pieces that already exist: CRIU, the standard Linux tool for checkpointing processes, and NVIDIA's cuda-checkpoint utility. A privileged node agent on every GPU node invokes both against live processes, according to Crusoe's write-up.

The Kubernetes surface is small. A PodSnapshot checkpoints a running pod. A SnapshotJob starts a pod from a template and checkpoints it as soon as it is ready. To restore, you add the annotation nvidia.com/restore-from to a new pod, naming the snapshot. The workload needs a short handshake: pause generation before the checkpoint and resume after restore. The repo ships examples for vLLM, SGLang and TensorRT LLM. The KV cache is released before every checkpoint, so it isn't part of the artifact.

Multi-GPU workloads are captured as one artifact across ranks on a single node, including TP, data plus expert parallelism, and decode context parallelism. Multi-node workloads are not supported.

2. The B200 numbers

NVIDIA's setup: B200, driver 615.71.09, VAST over NFS for storage, vLLM 0.31.0, SGLang 0.5.21, TensorRT LLM 1.3.0. Cold start is timed from process launch to engine-ready; restore is timed from the restore request to serving. Both exclude image pulls and container runtime setup. A selection from the post's Table 1:

Model Engine GPUs Weights (GB) Checkpoint (GB) Checkpoint time (s) Cold start (s) Restore (s)
Qwen3-14B vLLM TP1 29.54 37.71 19.98 122.76 5.72
gpt-oss-120b SGLang TP4 65.25 693.89 174.20 240.17 29.64
GLM-5.3-NVFP4 vLLM TEP8 464.82 604.00 282.80 393.65 28.64
DeepSeek-V4.1-Flash vLLM TEP8 510.30 647.18 274.75 1110.65 30.96
DeepSeek-V4-Pro-NVFP4 vLLM TEP8 913.09 996.53 193.84 908.48 39.56

Across all 22 configurations, restore took 3.6 to 42.7 seconds, 8x to 36x faster than cold start. The largest MoE configurations, with checkpoints of roughly 600 GB to 1 TB across eight GPUs, came back in under 43 seconds against 6 to 19 minutes cold.

3. Weight loading is not where the time goes

The breakdown table (Table 2) is the part I found most useful, because it splits cold start into startup, model load, initialization, and compilation plus autotuning plus graph capture.

For DeepSeek-V4.1-Flash on vLLM at TEP8, the cold start of 1,110.65 seconds breaks down as 63.96 s startup, 184.90 s model load, 77.25 s initialization and 784.54 s of compilation, autotuning and graph capture. By my arithmetic, that last phase is about 71% of the total and model load is about 17%. For GLM-5.3-NVFP4 on vLLM, compilation is 213.42 of 393.65 seconds, about 54% (my arithmetic).

If you've been optimizing cold start by putting weights on faster storage or streaming them in, these numbers say you've been attacking the smaller part. Snapshot's value is that it skips the compile and graph capture work along with the weight read, which no amount of storage tuning does.

4. Restore is a storage problem

The restore side (Table 3) splits into agent setup, CRIU restore of CPU process state, CUDA restore of GPU memory, and wake/remap. For the 8-GPU MoE runs, CUDA restore took 18 to 29 seconds and CRIU 4.2 to 10.8 seconds. For GLM-5.3 on vLLM, CUDA restore was 20.61 of 28.64 seconds.

Crusoe took this further on HGX B300 with GLM-5.3, comparing an NFS-backed artifact with local NVMe (cold page cache, Snapshot v0.2.0-rc.2 plus their PR #602):

  • Moving 594 GB of GPU state took 15.0 s from NVMe (about 40 GB/s) versus 33.3 s from NFS (about 18 GB/s).
  • Total agent restore fell from 41.4 s to 22.9 s.
  • CRIU restore stayed at about 5 s on both backends.
  • Pod created to Ready fell from 50 s to 31 s, against roughly 8 minutes cold, which they report as about 15.5x.

Their summary is "storage is the lever," and the numbers back it: once the artifact sits on local NVMe, CRIU and pod lifecycle overhead (about 8 of the 31 seconds sits outside the agent's work) are what's left.

Saturn Cloud ran a different measurement on a Nebius 8x B300 node with six 3.84 TB NVMe drives in RAID0: pod creation to first successful reply, vLLM 0.31.0, Snapshot 0.2.0-rc.3. GLM-5.3-NVFP4 went from 8m22s to 8m29s cold to 33 to 34 s restored; single-GPU Qwen3-14B, Qwen3-32B and GPT-OSS-120B went from 1m51s to 2m44s cold to 6 to 9 s. Their cold runs used a warm file cache, and they note these are one paired run per small model and two for GLM, not averages. Their GLM snapshot was 564 GiB, which by my conversion is about 606 GB, consistent with NVIDIA's 604.00 GB GLM-5.3 checkpoint on vLLM.

Neither partner is fully independent of NVIDIA: Crusoe co-tuned with the Snapshot team, and Saturn is a DSX ecosystem partner. But they ran on different hardware (B300 versus B200), different storage, and with their own timing boundaries, and landed in the same place.

5. Two things the tables show that the post doesn't discuss

Checkpoint size can be far larger than the weights. For gpt-oss-120b on SGLang at TP4, the checkpoint is 693.89 GB for 65.25 GB of weights, about 10.6x by my arithmetic, while the same model on vLLM at TP4 checkpoints at 119.69 GB. For DeepSeek-V4-Pro-NVFP4 on vLLM the ratio is about 1.09x. The post doesn't explain the SGLang TP4 figure, and since restore time is dominated by moving GPU state, I'd measure artifact size per engine and parallelism before budgeting storage.

Breakeven is the first replica, but barely in one case. NVIDIA says checkpoint plus restore was shorter than one cold start in every configuration. The tightest one is gpt-oss-120b on SGLang at TP4: 174.20 + 29.64 = 203.84 seconds versus a 240.17-second cold start, about 85% (my arithmetic). For the big MoE models it's not close: DeepSeek-V4.1-Flash on vLLM is 305.71 seconds versus 1,110.65.

6. The constraints that will bite

The workload contract and prerequisites are worth reading before anyone gets excited:

  • Drivers. Kernel-mode driver 580 or newer. Multi-GPU workloads need GPU CustomStorage, which needs CUDA driver API 13.4, meaning user-mode driver (libcuda.so) 615 or newer in every relevant process. Without it, a multi-GPU restore "takes too long and uses too much memory to be practical."
  • Cluster. GPU Operator 26.3 or newer with MIG disabled, Linux 5.13 or newer, a ReadWriteMany volume (or S3 in releases after v0.2.0), and a privileged DaemonSet with hostPID, hostIPC and hostNetwork. That last item will be a security review in most shops.
  • Same GPU model and driver on the restore node, and a CPU that has every instruction set the source had. The agent refuses a restore with a named missing flag, but only for flags on its list.
  • Engine settings. Workers must use spawn, not fork (for vLLM, VLLM_WORKER_MULTIPROC_METHOD=spawn). Transports CRIU can't restore must be off, for example TLLM_NCCL_SYMMETRIC_ZERO_COPY=0 and UCX_TLS=tcp,self. io_uring is blocked by a seccomp profile. File handles must be reopenable, so HF_HUB_DISABLE_XET=1 and HF_HUB_OFFLINE=1.
  • Mounts are part of the contract. Crusoe's restore failure showed up as binfmt_misc: Operation not permitted, but the real cause was a missing /cache/vllm mount in the restore pod. Their fix (PR #532) now names the missing mount before CRIU runs.

7. What I'd take from it

  • For 8-GPU MoE replicas, cold start is mostly compilation and graph capture, not weight loading. Snapshot skips both.
  • Restore speed is set by how fast you can move GPU state. Local NVMe roughly halved it versus NFS in Crusoe's test.
  • Scale-to-zero for large models starts to look realistic at 30 to 40 seconds of restore, but only within one node, one GPU model and one driver.
  • Expect to rebuild artifacts whenever you change the engine version, driver or GPU SKU, and budget storage per configuration, not per model.

In my Dynamo 1.6 notes last month, Snapshot came up only because snapshot mode stopped forcing some NCCL variables off. The contract above now asks for TLLM_NCCL_SYMMETRIC_ZERO_COPY=0 explicitly, so set it yourself. Snapshot now lives in its own repository with its own releases, and I'd treat it as part of the serving stack, not an add-on.
