vLLM 0.34 Upgrade Notes: Bigger KV Cache by Default, 64-Token Blocks, and No More V1 Runner

16 November 2026 · Anpoo Sivanadi

vLLM v0.34.0 was published at 23:22 UTC on November 16, 2026, which was 3:22 PM PT. The release notes count 1,061 commits from 412 contributors, 120 of them new. The repo has a v0.33.0 tag, but no v0.33.0 release was ever published on GitHub; the last release before this one was v0.33.0rc3 on November 2.

As with my 0.32 notes, I'm skipping most of the model-specific kernel work. What matters when you roll a new image across a fleet is the default that changed under you. This release has three of those that touch memory, startup and request latency on every model, plus a handful of removals that fail loudly. Numbers below come from the release notes and the linked PRs. Anything that is my own reading is labeled that way.

1. The KV cache is now sized after warmup, and gpu_memory_utilization defaults to 1.0

This is the biggest operational change. PR #56492 turns on what the project calls the extensible KV cache, by default on CUDA and ROCm.

The problem it solves is old. Captured CUDA graphs bake in the KV cache's addresses, so the cache has to exist before capture. That meant vLLM sized it from a profiling run that happened before graph capture and warmup, then left slack to absorb whatever it couldn't measure: graph memory, attention workspaces, sampler and logprobs buffers, spec-decode drafts. The PR describes that slack as the gpu_memory_utilization=0.92 default, 8% of the device, or about 15 GiB of a 192 GiB GPU sitting idle.

The new path reserves the cache's full address range with the driver's virtual memory API and backs only the blocks that capture and warmup actually touch. After warmup each worker measures what is really free, and the engine maps more physical memory into the same range. Addresses never move, so the captured graphs stay valid.

What the PR and release notes report:

Claim Source
4–10% more KV cache tokens (4.9–11.3 GiB per GPU) across eight models on GB200 PR #56492
MiniMax-M3 on H200: 433k to 672k tokens Release notes
Engine init time, excluding weight loading, down 21–34% (5–34 s) PR #56492
End-to-end startup down 6–18% PR #56492
TPOT up 6–18% on some H200 models at concurrency 128 Release notes

Two details I'd read twice. First, the latency trade-off is real and the project says so: a larger cache admits more concurrent requests, and per-token decode latency can rise. If you have a TPOT SLO tighter than your throughput target, test at your actual concurrency before rolling. Second, the PR notes that if you pin gpu_memory_utilization=0.92 explicitly, the cache comes out 1–4% smaller than before, because it now subtracts graph and warmup memory it measured instead of letting the slack absorb it. So "I'll just keep my old flag" does not give you the old cache size.

To opt out, the release notes give --gpu-memory-utilization 0.9 or --no-enable-extensible-kv-cache. If you share a GPU between processes, the utilization setting is still a cap, and PR #66704 adds a startup warning when an explicit value withholds memory from the cache.

My reading: a fleet that sets gpu_memory_utilization in a Helm chart or launch script out of habit should look at that value again. It used to be headroom against OOMs. Now it mostly costs cache.

2. Default --block-size is 64, except on ROCm

PR #63231 changes the default from 16 to 64 tokens per KV block. An explicit --block-size still wins, and attention backends that declare a preferred size still override the default. ROCm keeps 16-token blocks for default runs so it stays on its native C++ paged-attention kernel, which supports 16 and 32, instead of falling back to the slower Triton path.

The PR's validation section is worth reading because it shows where 16 was baked in. The first CI run with only the default change failed in offloading-connector chunk sizes, shared-storage connector hash counts, an autotune cache-key test, and a 25-minute MI250 hang in RocmAttn with 64-token blocks. All were fixed in the PR, and the MI250 job went from timeout to passing in 8m51s.

My reading: those failures are a list of the places your own setup might also assume 16. If you run a KV connector or offload tier, check that its chunk size and prefix-hash assumptions still line up with the GPU block size. Prefix-cache hits are also tracked per block, so coarser blocks can mean fewer full-block hits on short shared prefixes. I haven't measured that on this release; it's the first thing I'd look at on a workload with many short system prompts. --block-size 16 restores the old behavior.

3. Model Runner V1 is gone

PR #63373 removes it. Model Runner V2 is now the only GPU runner. VLLM_USE_V2_MODEL_RUNNER=0 now fails at startup instead of silently selecting the old path, so a leftover env var in a deployment manifest will turn into a crash loop. Custom V1 logits processors need to move to vllm.v1.worker.gpu.sample.logits_processor.

On the positive side, dual-batch overlap now runs on MRV2 with speculative decoding and DCP (#61464), and suffix decoding runs on MRV2 with a GPU speculator, so Arctic Inference is no longer needed for it (#60339).

4. Removals that fail loudly

These won't degrade quietly; they stop the server or the load. Still worth grepping your configs for before the rollout:

  • ROCm 7.2 images and wheels are dropped. Release artifacts are ROCm 10.0 only, and -rocm72 tags are no longer published (#61939).
  • huggingface_hub >= 2.0.0 is required, along with tokenizers >= 0.23.3 and timm >= 1.0.30 (#64779). If you build your own image with pinned deps, this is where it breaks.
  • fp_quant checkpoints no longer load, since QuTLASS and fp_quant were removed (#65230).
  • Marlin W4A8 is removed. The replacement is --quantization humming with VLLM_HUMMING_INPUT_QUANT_CONFIG instead of VLLM_MARLIN_INPUT_DTYPE (#65542).
  • Keye-VL and Keye-VL-1.5 are removed (#64287).

5. Quieter defaults worth knowing

  • NUMA binding is on by default, best effort, with --no-numa-bind to disable (#61258). If you already pin workers with numactl or a Kubernetes CPU manager policy, check that the two don't fight.
  • The default CUDA image now ships the AWS EFA userspace (libfabric, aws-ofi-nccl). A separate -efa image adds DeepEP built for EFA and routes NCCL over EFA by default (#65576).
  • VLLM_COMPILE_ON_ONE_RANK is on by default, giving a device-neutral compile cache, and all graph-affecting config fields are now hashed into compile cache keys (#63247, #65652). If you share a compile cache across nodes, expect a cold cache on the first start.
  • num_redundant_experts defaults to the minimum valid value (#30614).
  • Kimi K3.1 groundwork landed, but K3.1 is not servable in this release. The notes say this directly.

6. New things I'd actually try

  • Checkpoint/restore over HTTP. /checkpoint/prepare, /checkpoint/status and /checkpoint/restore, built on CRIU and cuda-checkpoint, in both the Python and Rust frontends (#62570). For cold-start-sensitive autoscaling this is the most interesting feature in the release.
  • Fault-tolerant DP+EP scale-down. Dead ranks are removed and their experts redistributed without a restart, through POST /v1/fault_tolerance/apply (#46370).
  • EP weight filtering. With --enable-ep-weight-filter and EPLB, DeepSeek-R1 NVFP4 at DEP8 reads 105 GiB per rank instead of 385 GiB (#64187).
  • NIXL on MI355X. Setting ucx_backend_params to rocm_ipc took transfer from 3.4 to 483.7 Gbps in the PR's test (#62905).

The headline speedups (up to 1.95x decode for Step5 NVFP4 MoE on 4×GB200, 1.6x output throughput for GLM-5.3-Flash with DeepGEMM FP8 MegaMoE, 1.24–1.40x faster GLM-5.3 TTFT at 32K–128K on GB200) are model-specific. Read them as "this model got faster," not as a fleet-wide number.

My rollout checklist

  1. Grep manifests for VLLM_USE_V2_MODEL_RUNNER, VLLM_MARLIN_INPUT_DTYPE, -rocm72 tags and fp_quant checkpoints.
  2. Decide on purpose whether to keep an explicit gpu_memory_utilization. Leave it unset unless you share the GPU.
  3. Run your real concurrency profile and compare TPOT, not just throughput.
  4. If you use a KV connector, offload tier or many short shared prefixes, compare block size 64 against 16 on cache hit rate.
  5. Check NUMA binding against your existing CPU pinning.
