GigaChat 4 708B: Three Linear Layers per Sparse One, and Where the Serving Memory Goes

27 November 2026 · Anpoo Sivanadi

Sber released GigaChat 4 on Thursday with open weights and an 83-page technical report. Most coverage, like Tech Times, led with the benchmark table. I care more about the architecture, because it stacks two long-context tricks I have written about separately, hybrid linear attention and DSA's indexer and top-k, into one 708B model. The report and the SGLang cookbook include enough serving numbers to see what that costs and buys.

One note up front: Sber is under US blocking sanctions. I worked only from the public report, model card, config and cookbook, and have not downloaded or run the weights.

1. The shape

From the config and Table 1 of the report:

  • 708B total, about 41B active. 64 layers at hidden size 7,168, the first 3 with dense FFNs. Each MoE layer picks 8 of 256 routed experts plus 1 shared expert.
  • 48 Gated DeltaNet (GDN) layers and 16 MLA layers, in a 3:1 pattern (every fourth layer is MLA). GigaChat 3.5 had the same ratio at 40 layers.
  • The MLA layers use DeepSeek Sparse Attention: a 64-head indexer scores every earlier token and attention runs over the top 2,048.
  • 1,048,576-token window via YaRN (factor 32 over a 32K base). Context was extended from 128K dense to 1M sparse with about 400B tokens of joint indexer and trunk training.
  • One built-in MTP layer, reused recurrently for drafting, plus a separate 5-layer BF16 DFlash2 drafter.

The released checkpoint is FP8 E4M3 with 128x128 weight blocks: 701B parameters in FP8 and 9.3B in BF16, about 726 GB of safetensors.

2. Where the per-request memory goes

The cookbook warns that SGLang keeps two pools for this model: a paged KV pool for the 16 DSA layers and a Mamba-style pool for the GDN recurrent and convolution states. Here is my arithmetic from config.json.

DSA cache. Each MLA layer stores a 512-value latent, 64 RoPE values and a 128-value indexer key per token. At one byte per value (FP8, scales excluded) that is 704 bytes per layer, or about 11.3 KB per token across 16 layers. A full 1M-token request needs about 11.8 GB.

GDN state. Each GDN layer keeps a 128x128 state for each of 64 value heads. Across 48 layers that is 50.3M values per request, about 201 MB in FP32 or 101 MB in BF16 (the cookbook's playground exposes state precision as a knob), plus under 5 MB of convolution state. This does not grow with context.

My read: for short and medium requests, the fixed state is the bigger term. At FP32 it equals the DSA cache of about 17,900 tokens. For the cookbook's 8K-in, 1K-out benchmark, the DSA cache is about 104 MB per request and the GDN state about twice that. Pool sizing for this model is a concurrency problem first and a context problem second, which matches the cookbook's advice to tune the state pool together with concurrency.

Parallelism changes the picture per GPU. The report notes that within an attention tensor-parallel group the MLA KV cache and indexer keys stay replicated. GDN state, by contrast, splits by heads. On the 16-GPU recipe, each H100 holds a full copy of every request's DSA cache but only a sixteenth of its GDN state. Weights take roughly 45 GB per GPU, and with --mem-fraction-static 0.8 that leaves on the order of 20 GB per GPU for both pools. A single 1M-token request would use more than half of it. The cookbook says the same thing more politely: a configured 1M window does not guarantee the server can admit a 1M request, so check max_total_num_tokens in the startup log.

3. What sparse attention buys, and when it does not

Appendix H of the report has useful numbers on DSA crossover points.

  • Decode, batch 1, 1M context, TP8: summed attention time across the 16 MLA layers is 7.497 ms with dense MLA and 2.622 ms with optimized DSA, about 2.9x faster. Baseline DSA was 3.132 ms. Indexer fusions and running MLA preparation on a second CUDA stream took off 16.3%.
  • Decode crossover: the estimated point where DSA beats dense moved from about 115K to about 15K tokens after those optimizations.
  • Prefill: at 220K input, sparse attention cut attention-kernel time from 433.38 to 100.33 ms (4.32x), but the full GPU step only from 825.77 to 492.16 ms (1.68x). At 10K input the sparse step was 14.5% slower because the indexer costs more than it saves.

That is why the serving stack picks dense or sparse separately for prefill and decode, with a K-only indexer filling the decode cache after a dense prefill. My take: anyone porting DSA should copy that switch, or pay indexer cost on exactly the short prompts that dominate chat traffic.

At the system level, Figure 5 shows prefill holding at about 79K to 82K input tokens/s from 50K to 200K context, and decode at about 3.0K to 3.4K output tokens/s at concurrency 64, both about 1.7x GigaChat 3.5 at 200K. Those runs use four GPUs with TP4, EP4 and DP4 attention. The report does not name the GPU, and decode is slower than GigaChat 3.5 below 40K.

4. Two H100 nodes, three decode modes

The cookbook's verified recipe is two 8x H100 80 GB nodes at TP16 on SGLang. The 8x H200 TP8 recipe is listed but marked not validated. The numbers below are 8K input, 1K output, greedy, P50, with throughput per GPU counting input and output tokens.

Mode Conc. 1 TPOT Conc. 16 TPOT / TTFT Conc. 64 tok/s/GPU / TTFT
No speculation 23.68 ms 42.07 ms / 8.0 s 310 / 28.9 s
Recurrent MTP (3 steps) 7.37 ms 24.78 ms / 2.6 s 409 / 14.0 s
DFlash2 (block 8) 4.26 ms 15.70 ms / 4.8 s 427 / 34.2 s

At concurrency 1 that is 42, 136 and 235 tokens/s per user. DFlash2 is 5.6x faster than plain decode and 1.7x faster than MTP. At concurrency 64 the gap between the two drafters shrinks to 4%, and DFlash2's TTFT is the worst of the three, because its effective running-request limit was 52, so some requests queued.

My read on the drafters: the report's Table 6 shows nearly identical mean acceptance lengths at up to 7 proposed tokens (4.49 vs 4.61 in instant mode, 4.51 vs 4.47 in reasoning mode). The H100 MTP recipe drafts only 3 tokens in sequential steps, so the latency gap comes mostly from DFlash2 proposing 7 positions in one pass, not from better guesses. For single-stream agent loops DFlash2 wins. For a busy shared endpoint, MTP gets nearly the same throughput without a separate 6.5 GB draft checkpoint.

Two more details are worth noting. In the cookbook, EP16 showed no output-throughput gain over EP1 at concurrency 16 or 64. And the report points to an NCCL fix for receive-proxy hangs in multi-node inference (PR #2390, closed on GitHub without a merge), so check your NCCL build before spanning two nodes. vLLM support is still an open PR (#69762).

5. The opposite bet, same week

China Telecom's Xing4.1-Preview (285B, 17B active, also 1M context) also uses MLA with DSA but drops linear attention entirely. Its model card says GDN's gating, state updates and scans lean on vector compute and operator fusion that are hard to exploit on the Ascend 910C software stack it trained on, while DSA is mostly matrix multiplies. My take: hybrid linear attention is a hardware-dependent choice, not a free win. GigaChat 4's stack is built on CUDA kernels (DeepGEMM, FlashMLA, Triton), which is what makes the GDN layers cheap.

6. What the benchmarks say

All model scores are Sber's own and unconfirmed. In reasoning mode, GigaChat 4 posts 80.89 on SWE-bench Verified (GLM-5.3: 86.67), 71.26 on Terminal-Bench 2.0 (GLM-5.3: 71.67) and 70.33 on AA-LCR. It trails badly on DeepSWE (35.40 against 74.34 for DeepSeek 4.1) and HLE text-only (23.91 against 43.42). Instant mode scores 80.82 on SWE-bench Verified, almost the same as reasoning mode, which is a useful cost lever if it holds up.

7. What this does not show

  • Every serving number is vendor-measured. The MTP and DFlash2 rows are single runs; only the no-speculation row is a median of three.
  • The cookbook table stops at 8K input. There is no end-to-end serving number for 1M-token requests.
  • The GPU behind Figure 5 is not named, and the H200 single-node recipe is untested.
  • My memory math assumes FP8 values and ignores scales, page padding and draft buffers. Treat it as a floor.
  • I have not run any of this.

My take

GigaChat 4 comes with an unusually detailed public write-up of a hybrid GDN plus DSA model at this scale, and the serving lesson is concrete. The DSA cache is small enough that 1M tokens fits on paper, but it is replicated under tensor parallelism, and the fixed GDN state dominates at normal request lengths. Size the state pool for concurrency, switch the indexer off for short prefills, and pick the drafter by traffic shape. Those lessons carry over to any hybrid model, whoever trains it.
