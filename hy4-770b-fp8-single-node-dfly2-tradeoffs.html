Hy4 Serving Notes: A 770B MoE on One 8-GPU Node, and What DFly2 Rules Out

21 November 2026 · Anpoo Sivanadi

Tencent first announced Hy4 as an API model on November 4. This week the weights followed: the instruct model in BF16, an FP8 checkpoint and a base model, with the Hugging Face model card last edited on the evening of November 19 PT. vLLM published a recipe on November 20 and SGLang has a cookbook entry with measured numbers.

I wrote about the smaller Hy4 Flash earlier this week. The flagship is a different problem. Hy4 Flash is about what you can push off the GPU. Hy4 is about whether a 770B model fits on one node at all, and what you give up to make it fast. Figures below come from the model card, config.json, the Hugging Face API, the vLLM recipe and the SGLang cookbook. Where the arithmetic or the opinion is mine, I say so.

1. The shape of the model

The language backbone has 770B parameters with 49B active per token. It has 78 layers: the first uses a dense FFN (intermediate size 18,432), and the other 77 are MoE layers with 256 routed experts, top-8 routing, one shared expert and an expert intermediate size of 2,048. Hidden size is 6,144 and the context window is 1,048,576 tokens. On top of that sit a 40-layer, 1.23B vision encoder and a five-layer, 3.3B DFly2 drafter. The vLLM recipe counts the stored total as about 774B, which matches the Hugging Face API.

Attention is where it gets interesting. Hy4 uses Multi-head Latent Attention (q_lora_rank 2,048, kv_lora_rank 512, 64 heads) combined with what Tencent calls Gated DeepSeek Sparse Attention: an indexer with 32 heads of dimension 128 picks the top 2,048 tokens each query attends to. It adds IndexCache, which reuses those sparse indices across layers. By my reading of indexer_types in the config, 21 of the 78 layers compute their own top-2,048 selection (layers 0 and 1, then every fourth layer from 5 through 77), and the other 57 reuse an earlier layer's selection. The residual path uses iHC (identity Hyper-Connections) with four residual streams.

2. Will it fit on one node?

The FP8 checkpoint is what makes single-node serving possible. Per the Hugging Face API, 762.8B parameters are stored as FP8 E4M3 and 11.6B in BF16, so about 98.5% of the weights are FP8 by my arithmetic. The config shows block FP8: 128 by 128 weight blocks with dynamically quantized, group-128 activations. SGLang lists what stays in BF16: the remaining attention projections, the DSA indexer, the first layer's attention and dense MLP, the shared experts, lm_head and the vision tower. vLLM notes this is not the MXFP8 format of Hy4-preview-FP8.

The sizes, as each project states them:

Checkpoint On disk vLLM aggregate GPU memory SGLang recipe
Hy4-FP8 ~786 GB, 245 shards ~944 GB 8x H200 or B200 at TP8, 4x B300 or GB300 at TP4
Hy4 (BF16) ~1.55 TB (vLLM: 1,549 GB) ~1,859 GB (8x B300) None; exceeds those configurations

vLLM wants one 8-GPU NVIDIA node and host RAM large enough to load the checkpoint. Neither project supports AMD Instinct for this model. vLLM says its ROCm port has neither the vision encoder nor the DFly2 drafter, even though it lists MI300X through MI355X in its hardware picker.

My arithmetic on headroom: at TP8 on H200, the FP8 weights take about 98 GB of each GPU's 141 GB, leaving roughly 43 GB per GPU for KV cache, activations and CUDA graphs. At TP4 on B300, weights take about 197 GB of 288 GB, leaving about 91 GB. Neither leaves much room.

3. The KV budget

MLA keeps a compressed latent per token per layer instead of full keys and values. With kv_lora_rank 512 plus a 64-dimension RoPE part, that is 576 values per layer. SGLang says the KV cache is BF16 by default, so my estimate is 576 x 2 bytes x 78 layers, about 88 KiB per token, before the indexer keys. That works out to about 11.8 GB for a 128K-token sequence and about 94 GB for a full 1M-token sequence.

The catch is tensor parallelism. MLA's latent is one shared vector, not per-head state, so TP replicates it rather than splitting it. SGLang's description of decode context parallelism implies the same: --dcp-size 2 "stripes the MLA latent KV across each rank pair", which only raises capacity if each rank held a full copy to begin with. Put my numbers together and each H200 at TP8 holds at most three or so full 128K sequences, and a full 1M-token sequence does not fit. On B300 at TP4 it is about seven 128K sequences, and 1M is still just over the line. These are rough upper bounds that ignore activations and indexer keys. That squares with the vLLM recipe, which starts from 131,072 tokens and 32 sequences and says plainly that "a full 1M-token request has not been validated for this recipe." For comparison, Tencent's own Hy4 Flash card claims Hy4 Flash's KV cache is one sixth the size of Hy4's.

SGLang offers two ways to stretch this on Blackwell (SM100, SM103, SM107): decode context parallelism and an FP8 KV cache (--kv-cache-dtype fp8_e4m3), which both switch the DSA backends to trtllm. On H200 the server refuses both at startup. A hierarchical KV cache can also write through to a host pool twice the size of each rank's device pool.

4. What DFly2 rules out

DFly2 is the reason to run the low-latency recipe. The five draft layers ship inside both checkpoints. Each draft layer reuses the KV cache and the top-2,048 selection of a matching target layer (the config pairs them with layers 61, 65, 69, 73 and 77), so the drafter has no KV pool or indexer of its own. One draft forward pass produces a seven-token block that one target pass verifies. The model card claims constant draft cost (about 2K keys per token at any context), zero extra KV memory, and "PD-disaggregation ready", since the drafter skips prefill.

The engines are stricter than the card. SGLang validates DFly2 before loading weights and refuses to start with any of these: DP-Attention, pipeline parallelism, prefill or decode context parallelism, PD disaggregation, an FP8 KV cache, LoRA, two-batch overlap or mixed chunked prefill. vLLM requires data, pipeline, prefill-context and decode-context parallel sizes of 1, which is why its recipe offers single-node TP only. So the design is ready for disaggregation, but no shipped recipe runs it that way yet. More to the point, every capacity knob in section 3 is mutually exclusive with the drafter. You pick latency or KV capacity per deployment.

There is a sampling trap too. SGLang verifies DFly2 drafts greedily. A request that sets no sampling fields decodes at temperature 0. But Tencent recommends temperature=0.9, top_p=1.0, and the checkpoint's generation_config.json carries temperature 0.9. In SGLang, a request that sets only top_p: 1 inherits that 0.9 and gets rejected. Grammar-constrained tool calls (tool_choice: "required", named functions, strict tools) are also rejected under DFly2. The vLLM recipe's examples send temperature=0.9 with DFly2 enabled and do not say how it verifies. If you run both engines, test this explicitly.

5. The measured numbers

SGLang publishes one verified benchmark, on its default cell (the playground names it H200, FP8, low-latency, TP8 with DFly2), with random 8,192-token inputs and 1,024-token outputs:

Concurrency TTFT p50 TPOT p50 Tokens/s per user Throughput per GPU
1 847 ms 5.78 ms 173.2 175.7 tok/s
64 66,692 ms 30.58 ms 32.7 708.3 tok/s

GSM8K on the same cell is 95.53%. Two readings of my own. First, 173 tokens/s per user at batch one on Hopper for a 49B-active model is good, and that is the drafter doing its job. Second, the 66.7 s TTFT at concurrency 64 is mostly queueing. The page warns that with DFly2 on, SGLang resets --max-running-requests to 48 when it is unset, so a 64-way benchmark leaves 16 requests waiting. Random-token inputs are also a poor test of draft acceptance.

6. Capability and limits

Tencent's base-model table puts Hy4 Base slightly ahead of DeepSeek-V4-Pro-Base on knowledge: MMLU-Pro 73.9 against 73.4, SimpleQA 57.2 against 52.1, SuperGPQA 62.7 against 54.8. It trails on code (MBPP-plus 74.0 against 79.1). On 579 finance tasks graded by 213 professionals, Hy4 scored 3.04 out of 4 against 2.97 for DeepSeek-V4.1-Flash-1017 and 2.68 for both Kimi K3.1 Pro and GLM-5.3. Tencent says plainly that a "notable gap remains" to top proprietary models on research math, long-horizon coding and advanced visual QA. All of this is self-reported, partly on internal benchmarks, and the license is the Tencent Hy License, not Apache or MIT.

My take

Hy4 is the largest open model I have seen ship with a single-node FP8 path in both major engines on day one, and the tight integration of the drafter with sparse attention is clever. For capacity planning, though, two numbers matter more than 770B. The first is about 88 KiB of replicated latent KV per token, which caps long-context concurrency hard on H200. The second is the list of features DFly2 switches off. If I were deploying it, I would run two pools: DFly2 at TP8 for interactive and agent traffic, with clients sending greedy requests, and a high-throughput pool on Blackwell with FP8 KV and decode context parallelism for long documents and batch work. Before committing hardware, I would want a validated long-context run, acceptance rates on real traffic instead of random tokens, and a disaggregated DFly2 configuration that actually starts.
