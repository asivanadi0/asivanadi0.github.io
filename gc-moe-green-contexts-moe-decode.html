Giving MoE Dispatch Its Own SMs: What GC-MoE Gets From Green Contexts on H20 and B300

4 November 2026 · Anpoo Sivanadi

The fastest MoE decode kernels today fuse everything into one persistent kernel: token dispatch, both expert GEMMs and the combine all run inside the same launch, on every SM. A new paper argues that at decode batch sizes this is the wrong shape. Its fix is to carve the GPU in two at the driver level and give dispatch its own small set of SMs.

"GC-MoE: Overlapping Expert-Parallel Token Dispatch with FP8/FP4 Grouped GEMM via CUDA Green Contexts" (Yong Li, Kan Liu and Tao Lan, with Alibaba addresses; arXiv 2611.04222, posted Nov 3) measures this against DeepGEMM's Mega MoE on eight H20s and eight B300s. GC-MoE is faster at all 54 measured points: 1.188 times on average on H20 and 1.106 to 1.123 times on B300. The code is on GitHub.

Here is the mechanism, the numbers, and what I'd check before trusting it in a serving stack.

1. Why the fused kernel leaves time on the table

Under expert parallelism, every MoE layer does four things: an all-to-all that sends each token to the ranks that own its experts, a grouped GEMM with SwiGLU, a second grouped GEMM for the down projection, and a combine back to the source ranks.

At decode each rank holds 1 to 256 tokens. The paper's example is GLM-5.2 with 256 experts, top-8 routing on eight ranks: at one token per rank, each expert sees 0.25 tokens on average, so the padded GEMM tile is almost all padding. The GEMM cost is streaming FP4 expert weights out of HBM, not arithmetic. Dispatch is latency-bound and needs only a few SMs to saturate NVLink.

Mega MoE already overlaps dispatch with compute, but it does so by sharing every SM. On B300, each CTA carries four dispatch warps next to two TMA-load warps, an MMA-issue warp, a scheduler warp and eight epilogue warps. The authors name three costs:

  • The GEMM never owns a whole SM. The dispatch warps and their staging buffers come out of each SM's register file and shared memory.
  • The sync domain is the whole device. Prologue and tail grid syncs span all 148 SMs on B300, so every phase waits for the slowest CTA.
  • Every replay ends with a cross-rank barrier. After the workspace clean, all ranks pass a second barrier before the next replay can reuse the workspace. That is an NVLink round trip per layer, per step.

2. The design

Green contexts arrived in CUDA 12.4. They let a process split the device's SMs with cuDevSmResourceSplitByCount and create a lightweight context over each part with cuGreenCtxCreate. Kernels launched into one context's stream only run on its SMs. No MPS daemon is involved.

GC-MoE creates two contexts once per CUDA context:

  • Communication partition: 20 of 148 SMs on B300. The default request is 16 SMs and the driver aligns it up to 20. On H20 the default request is 4.
  • Compute partition: the remaining 128 SMs on B300.

Each MoE layer is a child CUDA Graph with three kernel nodes. The dispatch kernel runs on the communication partition and the grouped GEMM kernel runs on the compute partition. Neither depends on the other, so the driver launches them at the same time on disjoint SMs. A finalize kernel depends on both and does the combine.

Three details make it work:

  • A token ring with block-level handshakes. Dispatch pulls tokens into a reused ring and marks each block full with a generation-tagged counter. The GEMM starts on the first full block instead of waiting for dispatch to finish.
  • No trailing barrier. Per-expert receive counters are double-buffered by parity. The finalize kernel flips the parity after it consumes the counts, so the next replay writes to the other buffer and no cross-rank rendezvous is needed between replays.
  • Balanced workqueues. Each green context gets its own hardware workqueue (CU_WORKQUEUE_SCOPE_GREEN_CTX_BALANCED, concurrency limit 1). The paper notes that without this, two contexts can land on one queue, which silently serializes the very kernels you meant to overlap. I think that is the most useful single line in the paper for anyone trying green contexts themselves.

The GEMMs are per architecture. On B300 the kernel uses the 2-CTA block-scaled tcgen05 MMA with operands swapped so the token count sets the N dimension, rounded up to 16 instead of the full block size. FP4 routed weights and FP8 shared-expert weights go through the same instruction sequence. The main addition over the baseline is prepacking FP4 weights into K128-contiguous tiles, so one TMA load is a single 8 KB burst instead of 128 strided segments. On H20, which has no native FP4 MMA, MXFP4 weights are decoded to E4M3 in registers and fed to register-A WGMMA, with block scales applied as fused multiply-adds outside the MMA.

3. The numbers

The setup is CUDA 13.2, PyTorch 2.11, DeepGEMM 2.8.2 as the baseline and GC-MoE 0.3.1. Each point is the slowest rank's median latency over 30 windows of 100 graph replays, with L2 flushed between windows. The sweep covers 1 to 256 tokens per rank.

H20, DeepSeek-V4.1-Flash, routed experts:

  • Faster at all nine points, 1.188 times on average.
  • 1.04 times at 1 token per rank, a plateau of 1.26 to 1.30 times from 4 to 32 tokens per rank, and down to 1.03 times at 256.
  • At 16 tokens per rank, 341.7 µs against 442.7 µs.

B300, routed experts:

  • GLM-5.2 averages 1.102 times and DeepSeek-V4.1-Flash 1.109 times. Every point falls between 1.085 and 1.189 times.
  • DeepSeek-V4.1-Flash at 1 token per rank: 59.4 µs against 70.6 µs. The eight rank medians are tightly clustered, so this is not one slow rank.
  • The win comes with fewer GEMM SMs: 128 against the baseline's 148.

Fused shared experts:

  • On B300 against Mega MoE's own fused shared-expert mode, the average is 1.123 times, with a peak of 1.209 times at 1 token per rank.
  • On H20 the average is 1.188 times, with a peak of 1.353 times. Here the baseline runs the shared expert as a separate kernel (more on that below).

The effective throughput tables tell the same story. On B300 with GLM-5.2 at 256 tokens per rank, aggregate matmul throughput goes from 7,525 to 8,491 TFLOPS. NVLink bytes are identical by construction; they just move in less wall time.

Accuracy holds. On H20 the minimum cosine against Mega MoE is 0.9999998, and the two kernels have the same maximum absolute error (0.109375). All 94 B300 cases pass.

4. What I'd discount

  • The H20 baseline is the authors' own port. DeepGEMM ships Mega MoE only for SM100. For H20 the authors built an SM90 reference port themselves, and it has no fused shared-expert path. The H20 numbers, including the 1.35 times peak, are against code that the people proposing the alternative wrote. I'd lean on the B300 numbers, where the baseline is the public kernel.
  • No partition-size ablation. The paper says plainly that it has no sweep over dispatch SM counts and no overlap-on versus overlap-off comparison. So we know 20/128 beats the fused kernel, but not whether 12 or 28 dispatch SMs would be better, or how much of the gain is the split versus the removed barrier versus the K128 weight prepack.
  • Operator latency, not serving latency. These are isolated layer replays at fixed token counts. There is no end-to-end tokens per second or inter-token latency in a serving engine yet, and integration is listed as future work.
  • Decode only, with hard shape limits. At 256 tokens per rank the gain shrinks to 1.01 to 1.13 times. The 64-bit completion bitmap caps the intermediate size, there is a 2,048-expert limit, and the workspace is single-instance, so calls that share it must be serialized.
  • Single node, NVLink only. Nothing here covers dispatch across an RDMA fabric.

5. What I'd take from it

  1. Treat SMs as a budget you can split. When a decode layer's GEMM is bound by weight streaming, the last 20 SMs buy little arithmetic. Spending them on a dedicated communication kernel was worth 9 to 19 percent on B300.
  2. Look for per-replay barriers. A cross-rank round trip at the end of every layer is easy to miss in a profile, because it looks like part of the kernel. Double-buffering the counters is a cheap way to remove it.
  3. Set the workqueue scope if you use green contexts. Otherwise two "concurrent" kernels may share one hardware queue and run back to back.
  4. Benchmark at your real tokens per rank. The H20 curve goes from 1.04 to 1.30 and back to 1.03 times across the sweep. An average speedup hides where your traffic actually sits.

My own opinion is that this is a better direction than ever-deeper fusion for decode. Splitting the device lets each kernel be tuned on its own, and the paper shows that costs less than giving up 13.5 percent of the SMs would suggest. I'd want the partition sweep and a vLLM or SGLang integration before I put it in production, but it is worth a weekend on any B300 node serving DeepSeek-class MoE.
