AICR v1.0: NVIDIA Freezes the Contract for GPU Kubernetes Recipes

6 October 2026 · Anpoo Sivanadi · based on AICR’s v1.0.0 release notes, NVIDIA’s October 6 technical blog, the README, and RELEASE.md

NVIDIA’s AICR v1.0.0 freezes the aicr CLI, aicrd REST API, Go SDK, and bundle schemas — a cluster configuration generator for GPU Kubernetes recipes, not a distribution or provisioner.

Most GPU cluster breakage I’ve seen isn’t caused by one broken component. It comes from a combination that used to work: a driver that moved a minor version, a GPU Operator chart that changed a default, a device plugin that a cloud image swapped underneath you, a kernel that nobody pinned. Every piece installs cleanly, and then a training job hangs at NCCL init or an inference pod sees zero GPUs.

NVIDIA’s AI Cluster Runtime (AICR) is an attempt to write those combinations down as data. v1.0.0 was tagged at 23:47 UTC on October 5, 2026 (4:47 PM PT), and NVIDIA’s technical blog post by Mark Chmarny and Nathan Taber followed on October 6. The headline is not a new feature. It’s a promise: the aicr CLI, the aicrd REST API, the Go SDK at pkg/client/v1, and the bundle layout plus artifact schemas are now frozen, and breaking any of them waits for v2.

That’s the part I care about. A recipe library only helps platform teams if they can automate against it without rewriting that automation every month.

What AICR actually is

The README is unusually direct about scope. AICR is “a cluster configuration generator.” It is not a Kubernetes distribution, not a provisioner, not a managed control plane. You bring a cluster and your deployment tooling, and AICR produces the runtime configuration your tools apply.

It does that through four pieces that are deliberately kept separate:

  • Snapshot records what is actually on a cluster: Kubernetes version, OS, kernel, GPUs, operators, topology. The snapshot agent runs as a Kubernetes Job and writes the result to a ConfigMap.
  • Recipe describes a desired, version-locked configuration for a target you name by service, accelerator, OS, workload intent and optional platform. Recipes are built from layered overlays (base, then cloud, accelerator, OS, workload) plus shared mixins.
  • Bundle renders a recipe into artifacts for Helm, Argo CD (app-of-apps or the Helm-chart variant), Flux, or Helmfile. One folder per component, with values, checksums and a README.
  • Validation compares a recipe with observed state and can run deployment, conformance and performance phases inside the cluster, then record signed evidence of the result.

The README’s quick start shows the shape of it: 

aicr recipe --service eks --accelerator h100 --os ubuntu \
  --intent training --platform kubeflow -o recipe.yaml
aicr bundle --recipe recipe.yaml --deployer argocd --output ./bundles
aicr validate --recipe ./bundles/recipe.yaml

The separation matters more than it looks. A snapshot is not a desired state, and a recipe does not reconcile anything. Your existing GitOps controller still owns the cluster, so adopting AICR doesn’t mean handing production to a new operator. For a team with Argo CD or Flux already wired into change management, that’s the difference between a tool you can trial this week and one that needs a quarter of design review.

Coverage, per the README, spans twelve service targets including EKS, GKE, AKS, OKE, OpenShift and RKE2; A100 through GB300 plus RTX PRO 6000, with VR200 in Preview; six OS families; and Dynamo, Kubeflow, NIM, Run:ai and Slurm via Slinky. Components include GPU Operator, the DRA GPU driver, Network Operator, NVSentinel, AWS EFA, GKE NCCL TCPXO, KAI Scheduler and Kueue.

What “frozen” means here

The RELEASE.md deprecation policy is the most useful document in the repo for anyone thinking about integrating. It defines, per surface, what counts as breaking. For the Go SDK that’s removing or renaming an exported identifier, changing a signature, narrowing a parameter type, or changing documented semantics without changing the name. For bundles and schemas it’s removing or renaming a bundle path, removing a schema field, tightening a type, adding a required field, or retiring an apiVersion. A breaking change that ships without the required notice is defined as “a release blocker, not a release note.”

Two details stood out to me.

First, the policy treats enum changes asymmetrically, and correctly. Adding a value to a response enum is additive for the server but breaking for a client that switches exhaustively on it, so it gets announced without owing a deprecation window. Adding a value to a request enum is always additive. Generated clients hit that first case all the time, and it’s rare to see a project write it down.

Second, the document is candid that the deprecation channel will “most likely reach v1.0.0 mechanically tested but never exercised on an obligation it actually owed,” and calls that “a deliberate, accepted position.” In other words, the rules exist and are enforced in CI, but no real removal has gone through them yet. The first actual deprecation under v1 will be the real test.

Support covers the latest minor and the previous one. One small thing: when I read RELEASE.md on main the evening of October 6 PT, its supported-versions table still listed 0.22.x and 0.21.x. Check it before you pin.

The blog says each public interface has a committed baseline checked before changes merge, and that the CLI and REST server share the Go SDK’s facade. That second point is underrated. Tools that expose a CLI, an API and a library often end up with three slightly different behaviors, and one shared facade is the cheap way to avoid that.

What changed in 1.0.0 itself

The items in the release notes I’d look at first:

  • Upgrade checks against live state. aicr upgrade-check --from cluster now compares against what is actually installed and warns about live objects an upgrade could destroy (#2840). Upgrade checks also catch changes to a component’s chart, source, path, type, manifests or object names, and bundles now carry deployer-specific upgrade steps when a pinned version needs them (#2986). Most real breakage happens on upgrade, not first install, so this is where I’d expect the most value.
  • Validation that proves capability, not just presence. A new slinky-slurm-gpu-access check verifies that a Slurm job given one GPU can use exactly that GPU, and that a job without one can’t open any (#3057). On GKE, checks now confirm that every a3 node exposes all 8 GPU NICs for GPUDirect-TCPXO rather than only checking that the Network objects exist.
  • Readiness gate fixes. The Helm readiness gate now blocks the deploy and re-runs on upgrade, and its Jobs schedule onto system nodes instead of sitting Pending on tainted GPU pools. That last one is a classic: a validation Job that tolerates no taints on a cluster where every worker is tainted.
  • Version moves. GPU Operator goes to v26.7.1, which drops a ComputeDomain CRD workaround. NVSentinel moves to v1.25.0. GB200 on GKE with Kubeflow gains a torch-distributed-rdma GPUDirect-RDMA training runtime that a TrainJob selects by name (#2859). VR200 recipes collapse two rebooting NodeWright CRs into one.

Signed evidence is the interesting long-term bet

Every AICR recipe carries build provenance signed by NVIDIA CI. Recipes with published evidence also carry what the README calls a “signer-bound, tamper-evident attestation” that binds an identity to a recorded aicr validate result. The validation dashboard lets you filter recipes by service, GPU, OS, intent and platform and inspect what was tested, which checks passed and who signed. The release supply chain claims SLSA Build Level 3 provenance, signed SBOMs and Cosign attestations, with aicr verify for offline bundle checks.

NVIDIA doesn’t have every cluster shape, so contributors can validate a recipe on their own hardware and submit signed evidence for maintainer review. If that works, the dashboard becomes a shared record of which combinations passed on which hardware, signed by whom. That beats a compatibility matrix in a PDF, because you can verify it yourself.

The limit is obvious: evidence is a point-in-time result on someone else’s cluster. It doesn’t tell you your fabric, firmware and node images match theirs. I’d treat it as a strong prior and still validate my own cluster after every change.

Adoption signals

The release notes say more than 85 people from more than 20 organizations have contributed since AICR launched at KubeCon EU in March, with more than 1,000 issues and 1,500 PRs. The blog puts it at over 100 distinct contributors, almost half from outside NVIDIA. The repo is Apache 2.0. Pulumi Labs publishes an AICR provider and Mirantis’s k0rdent lists AICR in its catalog, a reasonable sign the schemas work outside NVIDIA’s own tooling.

What I’d do with it

If I were bringing this to a production GPU cluster, I wouldn’t hand AICR my deployment pipeline on day one. I’d start with the read-only pieces. Run the snapshot agent on an existing cluster, generate the recipe that matches its shape, and run aicr validate against it, starting with the declarative constraint checks rather than the in-cluster phases. That tells you how far the cluster sits from a configuration someone has actually validated, without changing anything. Keep snapshots over time and use aicr diff to catch drift between clusters or between weeks. Then make aicr validate a post-change gate in CI, especially around GPU Operator and driver upgrades. Only after that would I render bundles into the GitOps repo.

The v1 contract is what makes that incremental path safe. Before this release, scripting against the CLI output or the bundle layout meant accepting churn. Now the churn has rules. Whether they hold up will show when the first real deprecation goes through.
