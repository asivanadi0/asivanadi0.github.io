NVIDIA's NVFP4 DeepSeek-V4.1-Flash: Smaller on Disk, Bigger on the GPU, and a vLLM PR You Have to Carry

31 October 2026 · Anpoo Sivanadi

On October 30, NVIDIA published DeepSeek-V4.1-Flash-1017-NVFP4, a Model Optimizer quantization of DeepSeek's October 17 checkpoint. The card's headline is a checkpoint that drops from about 475 GiB to about 400 GiB with benchmark scores that barely move, served on four GB300 GPUs.

That summary is true, but it hides where the bytes actually went. I pulled the safetensors headers for all 48 shards of both repos and summed them by component. The 75 GiB saving does not come from the experts at all. It comes from the Engram lookup tables, which on this command line live in host memory, not HBM. The experts actually got slightly bigger.

1. What NVIDIA changed

The card describes two conversions, and the config.json matches it:

  • Routed experts, MXFP4 to NVFP4, weights and activations (W4A4). The w1, w2 and w3 projections of all 384 experts in all 40 layers move to NVFP4 with group size 16. The config marks only layers.N.ffn.experts as NVFP4 and ignores *.attn.*, *.ffn.shared_experts.*, head and mtp.*.
  • Engram tables, FP8 to MXFP4. The two Engram embedding tables (layers 1 and 14, 384,006,168 and 384,016,682 rows) go from FP8 E4M3 to packed E2M1 with UE8M0 scales per block of 32 (engram_embed_quant: mxfp4).

Everything else (attention, shared experts, vision tower, MTP heads) keeps its source precision. Calibration used 1,024 samples at sequence length 512, half from cnn_dailymail and half from Nemotron post-training data. Per the card, 24 of the 46,080 expert projections fell back to default activation scales.

2. Where the bytes went

Here is what the shard headers add up to. These are my sums from the published files, not numbers from the card:

Component Source (MXFP4 experts, FP8 Engram) NVIDIA NVFP4 Change
Routed experts 275.67 GiB 291.49 GiB +15.82 GiB
Engram tables 189.13 GiB 97.57 GiB -91.56 GiB
Attention 4.87 GiB 4.87 GiB 0
Embeddings and head 2.47 GiB 2.47 GiB 0
Shared experts, vision, MTP, other 3.11 GiB 3.11 GiB 0
Total 475.24 GiB 399.51 GiB -75.73 GiB

The expert growth is just scale overhead. In the source, each expert matrix is packed FP4 (two values per I8 byte) plus one F8_E8M0 scale per 32 values, which works out to 4.25 bits per weight. In the NVFP4 file it's the same packed payload plus one F8_E4M3 scale per 16 values, a single FP32 weight_scale_2 per tensor and an FP32 input_scale for activations, so about 4.5 bits per weight. You can see it in one tensor: layers.5.ffn.experts.7.w1 keeps a 5,898,240-byte weight, but its scale tensor doubles from 368,640 to 737,280 bytes. Scaling 275.67 GiB by 4.5/4.25 gives about 291.9 GiB, which matches the file.

The Engram tables are the opposite story. Each row in the source is 256 bytes of FP8 plus 8 scale bytes. In the NVFP4 repo it's 128 bytes of packed FP4 plus the same 8 scale bytes. With about 768 million rows across the two tables, that halving accounts for more than the whole checkpoint shrink.

3. What that means on a GB300 node

The card's reference command runs on four GB300 GPUs with tensor parallelism 4 and --engram-config '{"cpu_offload":true}'. With offload on, the Engram tables are in pinned host memory. So, by my estimate:

  • GPU-resident weights grow. Everything except Engram comes to about 301.9 GiB in the NVFP4 checkpoint versus about 286.1 GiB in the source. Split evenly over four GPUs that's roughly 75.5 GiB per GPU instead of 71.5 GiB. This is an estimate: some small pieces may be replicated per rank.
  • Host memory is what shrinks. The Engram tables go from about 189 GiB to about 98 GiB per serving instance. How that splits across ranks depends on vLLM's Engram configuration, but either way you free about 90 GiB of pinned host memory per instance.
  • The reason to switch is compute, not capacity. W4A4 means the expert GEMMs take FP4 activations as well as FP4 weights, which is what Blackwell's FP4 tensor cores are built for. The card lists Blackwell as the only supported microarchitecture, so this checkpoint is not for Hopper.

If you are running several DP replicas on one host, the host saving compounds. The vLLM PR behind this checkpoint measured a DP=4 setup with one shared MXFP4 Engram table at 48.64 GiB across all four replicas, using {"dp_shared_memory": true}. That figure is from the PR's test on the earlier V4.1-Flash release, so I wouldn't assume it carries over exactly to the 1017 tables.

4. "Lossless" means the weights, not the outputs

The card says all 16,986,931,200 expert weight blocks passed lossless conversion, "preserving dequantized weight values with signed-zero canonicalization." That number checks out: 384 experts times 40 layers times three 5,120 x 2,304 projections is about 543.6 billion weights, and dividing by 32 gives exactly that block count.

My reading of why it can be lossless: an MXFP4 block scale is always a power of two, and E4M3 can represent powers of two exactly across a wide range. Splitting each 32-value block into two 16-value halves that both use that same power of two, with the per-tensor FP32 scale absorbing the offset, reproduces every value bit for bit as long as a tensor's scales fit inside E4M3's exponent range. The only change is that negative zero becomes positive zero.

The card is careful to add that "lossless weight conversion does not imply identical inference outputs." Two things are actually lossy:

  1. Activations. They're now quantized to FP4 in groups of 16 against a static calibrated per-tensor scale. The calibration samples were only 512 tokens long, for a model with a 1,048,576-token context.
  2. Engram. Going from 8-bit to 4-bit values is a real precision cut.

5. What the evals show

The card reports these vLLM results at reasoning_effort=max and temperature=1.0, in percent:

Precision GPQA Diamond AA-LCR SciCode IFBench MMMU-Pro Terminal-Bench 2.1
MXFP4 (source) 92.77 80.41 57.58 76.33 78.38 81.81
NVFP4 + MXFP4 Engram 92.93 80.19 57.32 76.47 78.73 81.11

The repeat counts are decent: GPQA 16, AA-LCR 16 per run over two runs, SciCode 8, Terminal-Bench two runs of eight trajectories per task. Three scores went up and three went down, and the biggest drop is 0.7 points on Terminal-Bench. AA-LCR is the one I care about given the short calibration, and it moved by 0.22 points. I read the table as no measurable regression on these tasks. It is not a long-context stress test past what AA-LCR covers, and MTP speculative decoding wasn't exercised at all.

On the Engram side alone, the PR's own numbers: GSM8K 0.967 packed versus 0.966 FP8, which the author calls within noise. A lookup microbenchmark shows host-pinned lookups at 365 versus 356 microseconds for 8,192 tokens, so offloaded mode barely notices. GPU-resident lookups are about 36% slower (156 versus 115 microseconds) because of the nibble decode. With this checkpoint you want offload on anyway.

6. Serving status today

  • vLLM: stock images can't load the MXFP4 Engram tables. The card's results used vllm/vllm-openai:v0.31.0 with #61530 applied. As of this evening that PR is still open and unmerged, last updated October 22. Its own notes say the /dev/shm sizing for shared tables still assumes FP8 rows, so it over-reserves by about 2x.
  • SGLang: not validated with this checkpoint, per the card.
  • Load time: the reference command sets VLLM_ENGINE_READY_TIMEOUT_S=3600. Expect a slow first start, and set your health-check grace periods to match.
  • Flags worth copying: --kv-cache-dtype fp8, --max-num-seqs 128, the FLASHINFER_MLA_SPARSE_DSV41 attention backend with an MXFP4 indexer KV, and --tokenizer-mode deepseek_v41 plus the matching reasoning parser.

7. What I'd check before switching

  1. Build vLLM with #61530 on top of a pinned commit, and plan to rebase when it merges or changes.
  2. Size host RAM for about 98 GiB of Engram tables per instance, or use dp_shared_memory if you run DP replicas on one host.
  3. Don't expect more KV headroom. GPU-resident weights go up by roughly 4 GiB per GPU at TP4 (my estimate).
  4. Benchmark expert GEMM time and end-to-end decode against the source checkpoint on your own traffic. The card publishes accuracy, not throughput, so the W4A4 speedup is the part nobody has measured in public yet.
  5. Run your longest real prompts and look for drift, since activation scales were calibrated on 512-token samples.
  6. Turn MTP on and measure acceptance yourself before trusting the eval table for speculative serving.

What makes this checkpoint useful is that it's honest about its parts: which tensors changed, which conversion is exact, which runtime patch it needs. Read the header sums before reading the size headline, though. The 75 GiB you save lands in host memory, and the GPU side gets slightly heavier in exchange for FP4 activations.
