OSPA: Meta, Microsoft and Alibaba Want Every AI Fabric Switch to Boot the Same Way

12 October 2026 · Anpoo Sivanadi · based on OCP’s October 8 OSPA announcement, the draft GitHub spec, and SDxCentral

On October 8, OCP posted Open Switch Platform Architecture, a draft under OCP review initiated by Meta, Microsoft, and Alibaba: a vendor-neutral switch platform layer so AI fabric SKUs can boot, inventory, and flash the same way.

On October 8, the Open Compute Project posted a new in-progress contribution to the Networking Project: the Open Switch Platform Architecture specification. It is a draft under OCP review. Meta, Microsoft, and Alibaba initiated it. The Revision 1.0.0 candidate is on GitHub. Tao Ren, Tian Fang, and Xu Wang (Meta), Ying Xie and Guohan Lu (Microsoft), and Yiyuan Huang and Zhiping Yao (Alibaba) are the named authors. You’ll hear it at the OCP Global Summit 2026 session, and on SDxCentral.

I care about this the same way I cared about Arista’s Etherlink SU-144 on ESUN and Upscale’s Token Fabric: the fabric story is moving from “which ASIC forwards” to “can I onboard the box without rewriting platform software.” SAI, FBOSS, and SONiC already made the data plane portable. The thing that still changes every SKU is how the switch boots, inventories a PSU, spins fans, and flashes an FPGA. That is OSPA’s layer. Treat it as a draft under OCP review, not a frozen contract.

The data plane is not the remaining lock-in

Ren’s OCP post is blunt: SAI, and its adoption by FBOSS and SONiC, made forwarding software portable. The switch platform layer is “the final frontier of proprietary fragmentation in open networking.” Device enumeration, thermal control, and firmware updates are still re-implemented for every hardware SKU. Identical ASICs from different manufacturers present completely different platforms to the operating system. That is the inefficiency OSPA is aimed at, and it is why the AI-fabric onboarding story is in the first paragraph.

The spec names seven functional areas: Power Management, Hardware Access, Hardware Inventory Management, Environment Monitoring and Control, Firmware Maintenance and Recovery, Debuggability, and Security. Scope is explicit. This is the platform management layer. Routing protocols and forwarding management are out. Pure hardware design details are out. Security is a heading with one sentence: comprehensive security specifications will be defined in subsequent revisions.

In-Host, not BMC-as-NOS

Two architectural models are on the page. In the OOB-Native model, the BMC runs fans, sensors, leak detection, inventory, and firmware, and the Host only forwards. OSPA focuses exclusively on the In-Host Model: the BMC is restricted to power management, Host bring-up, leak protection, and troubleshooting — an independent path to recover an unresponsive Host. Everything else (sensors, fans, inventory, firmware) runs on the Host, in the same software ecosystem as the NOS.

That split is the boot story in the title. If platform services live on the Host, a new ODM SKU is a configuration file plus drivers the Host already has, not a second BMC personality. The spec still requires OOB Ethernet, serial console, IPMI, USB, and dedicated power-management interconnects between BMC and Host. The BMC can power-cycle the whole switch, the Host plus data plane, or the Host CPU only.

IOB FPGA over PCIe, then a tree of APEs

The Host-side topology hangs off I/O Bridge (IOB) FPGA(s) on PCIe. Each FPGA aggregates I2C, SPI, GPIO, MDIO, and LED controllers into a memory-mapped, low-latency path. Fragmented sideband buses are the thing this replaces. Output states — optics reset and LPMode, LED levels, GPIO outputs — must survive Host CPU and PCIe link resets and only clear on a switch-level power cycle or an explicit software request.

Inventory is an Atomic Platform Entity (APE) tree. An APE is the smallest unit platform software tracks: a FRU (PSU, fan tray), a standalone PCBA (switch main module), or several boards grouped as one logical APE when they are software-transparent. One Root APE. Children hang off parents. Enumeration is top-down. You do not talk to a child until the parent is up. Hot-swap APEs need a presence GPIO; access when presence is de-asserted is prohibited.

IDPROMs identify APEs. The Root APE IDPROM sits on the Host CPU’s embedded I2C/SMBus so it is readable before the rest of the tree. The Platform Identifier IDPROM (product name, serial, asset tag) lives on the chassis or blade, never on a field-swappable part, and must be reachable from both BMC and Host — two copies with identical content are acceptable. Formats are customer-specific: Meta EEPROM format v6 or ONIE TlvInfo. Product name from dmidecode -s system-product-name must match the Platform Identifier IDPROM. Discovery loads config from that name, not from the IDPROM, because the IDPROM’s bus and address are themselves platform-specific.

The worked example is Meta Minipack3. The Main Carrier Board is the root APE. The IOB FPGA on that board is the I2C/SPI/MDIO/GPIO fan-out. Platform Device Discovery reads dmidecode, initializes the MCB IDPROM on the CPU-embedded I2C bus, applies EVT/DVT/PVT and hardware-variant config, then walks children. That is the “boot the same way” claim in operator language: same walk, different JSON.

Power that does not wait on software

PSUs are PMBus-observable. FRU PSUs are tool-less and hot-swappable; the PSU fan is the FRU’s problem, not the platform thermal service. Presence and Power_Good go to Host GPIO or CPLD; PSU_PSON goes to the BMC. AC configs must support N+1 redundancy or better with active current sharing. Over-temperature restores automatically once it clears (OTP). Overcurrent (OCP) and overvoltage (OVP) latch off and need a manual power-cycle.

On a switch-level power cycle, the BMC comes up by itself. The Host — CPU, ASICs, optics — stays off or in reset until the BMC, or the Host Bringup watchdog, turns it on. The watchdog’s default timeout is 5-minute. A configurable timeout in non-volatile storage is nice to have. The BMC disables the watchdog once Host power-good asserts. If the Host is already on when the timer expires, the watchdog must not change the power state. First Host power-on: ASICs come out of reset without Host software; optics stay in reset until Host optics management takes them out; the ASIC must always enumerate on PCIe across Host CPU resets without software.

Front-panel OOB is two management ports, customer choice: 2x1G RJ45 or 1x1G RJ45 + 1x10G SFP+. An unmanaged/EEPROM-configured oob_switch (example: Marvell 88E6321) sits between BMC, Host, and those ports. NC-SI is explicitly discouraged. After a power cycle the switch loads EEPROM by itself; BMC or Host reset must not take OOB down. Optics get a dedicated I2C controller each — no muxes — at a minimum 100KHz, with firmware-upgrade clocks in the 400KHz to 1MHz range as a should, confirmed with the customer. LEDs: System, Power, Fan, and Leak (liquid-cooled only). Intensity is 8-bit per R/G/B channel (256 levels). Blink states are Solid, FAST (0.5s period), and SLOW (2.0s period), exposed through the Linux LED class at /sys/class/leds.

Fans, excluding PSU fans, boot to a platform-validated safe PWM without waiting on the thermal service. A fan watchdog is disabled at power cycle, kicked in normal operation, and on expiry drives those same fans to the safe PWM. ASIC overheat protection is not “trust the die.” An external sensor (example: MAX6581) on the on-die thermal diode alerts a CPLD, which de-asserts the VRM enable. The shutdown latches; ALERT de-assertion must not restore power. Liquid leak detection must work if Host and BMC software are dead: major leak kills Host (CPU, ASICs, optics); BMC stays on auxiliary power to log; the leak LED is hardware-driven.

Firmware: SPI, A/B, dual-path — and a ten-row customer list

SPI flash is the preferred upgrade path so flashrom and flashcp work. JTAG is not preferred; there is no standard Linux user-space ABI. I2C is not the primary firmware path except where a device standard forces it (PMBus PSUs, CMIS/SFF optics, small EEPROMs). Critical images get A/B banks and dual-path recovery. Host is the primary updater; BMC recovery is the fail-safe. On Minipack3, IOB FPGA and UEFI/BIOS have an independent BMC path.

Host software is three layers: IOB FPGA controller drivers (PCIe umbrella plus Linux auxiliary bus, not MFD), Platform Device Discovery from a config file such as platform_device.json, and hardware-agnostic services that only see stable symlinks (example: /run/devmap/xcvrs/xcvr_io_1 → /dev/i2c-15). The IOB ioctl header lives at fbiob-ioctl.h. The drivers are deployed across over 10 FBOSS platforms. Discovery code is platform_manager. The OCP tenets section says the same stack has proven deployment across over 10 production switch platforms, and that a configuration-driven design enables platform onboarding in under one day. Those are the spec’s numbers, not a measurement of my own.

What I would ask before I treat this as a bring-up contract

SAI made the forwarding API reusable. OSPA is trying to do the same for the software you run before the first packet — the way AICR froze a contract for GPU Kubernetes recipes, except here the unit is a switch SKU, not a cluster recipe. The IOB drivers and Minipack3 walk are the evidence that this is not a greenfield slide. The open questions are the ones the checklist already admits, plus a few I would still ask:

  1. Which non-FBOSS NOS trees — SONiC images in the wild, vendor EOS/NX-OS-class stacks — have loaded an OSPA platform_device.json without a fork of the IOB umbrella driver?
  2. Is “onboarding in under one day” measured on a second Minipack3-class board, or on a new ASIC with a new IOB bitstream?
  3. When does the Security chapter exist, and does it constrain BMC-to-Host USB gadget and SPI bus switching used for Host recovery?
  4. Who ships the first OSPA-labelled AI fabric SKU that is not a Meta Minipack, and at what date relative to this draft under OCP review becoming an approved OCP contribution?

Until those rows fill in, I would read OSPA the way I read ESUN 1.0: a vendor-neutral reference you can design against, with working FBOSS code behind the IOB chapter, and with the Foundation review stamp still on the cover. The useful test is whether the next ODM box boots into the same APE walk.
