OSPA: Meta, Microsoft and Alibaba Want Every AI Fabric Switch to Boot the Same Way

12 October 2026 · Anpoo Sivanadi · based on OCP’s October 8 OSPA announcement, the draft GitHub spec, and SDxCentral

On October 8, OCP posted Open Switch Platform Architecture, a draft under OCP review initiated by Meta, Microsoft, and Alibaba: a vendor-neutral switch platform layer so AI fabric SKUs can boot, inventory, and flash the same way.

On October 8, the Open Compute Project posted a draft under OCP review: Open Switch Platform Architecture, a spec of roughly 10,000 words, initiated by Meta, Microsoft, and Alibaba, with collaborative input from Accton, Arista, Celestica, Cisco, DTI, Micas, Nexthop, Nvidia, and Wistron. The Revision 1.0.0 candidate is on GitHub. SDxCentral covered it the same week. You’ll hear it at the OCP Global Summit 2026 session.

SAI, FBOSS, and SONiC already made the data plane portable. What still changes every SKU is the platform layer: how the box inventories a PSU, spins fans, flashes an FPGA, and brings the Host up when the BMC is wedged. That is the software you run before the first packet. I care about this the same way I cared about Arista’s Etherlink SU-144 on ESUN and Upscale’s Token Fabric: the fabric story is moving from which ASIC forwards to whether you can onboard the box without rewriting platform software. Treat it as a draft under OCP review, not a frozen contract.

The remaining lock-in is the platform, not the ASIC

Tao Ren’s OCP post calls the switch platform layer “the final frontier of proprietary fragmentation in open networking.” Device enumeration, thermal control, and firmware updates are still re-implemented for every hardware SKU. Identical ASICs from different manufacturers present completely different platforms to the operating system. OSPA’s answer is a vendor-neutral reference architecture across seven functional areas: Power Management, Hardware Access, Hardware Inventory Management, Environment Monitoring and Control, Firmware Maintenance and Recovery, Debuggability, and Security.

Scope is explicit. This specification is limited to the switch platform management layer. Routing protocols and forwarding management are out. Pure hardware design details are out. Security is a heading with one sentence: comprehensive security specifications will be defined in subsequent revisions.

Two models are on the page. In the OOB-Native model, the BMC runs fans, sensors, leak detection, inventory, and firmware, and the Host only forwards. OSPA focuses exclusively on the In-Host Model: the BMC is restricted to essential supervisory tasks — power management, Host bring-up, leak protection, and troubleshooting — serving as an independent mechanism for recovering an unresponsive Host. All remaining platform management services run on the Host, in the same software ecosystem as the NOS.

If platform services live on the Host, a new ODM SKU is a configuration file plus drivers the Host already has, not a second BMC personality. The spec still requires OOB Ethernet, serial console, IPMI, USB, and dedicated power-management interconnects between BMC and Host. The BMC can power-cycle the whole switch, the Host plus data plane, or the Host CPU only.

IOB FPGA, APE tree, IDPROM

The Host-side topology hangs off I/O Bridge (IOB) FPGA(s) attached over PCIe. Each FPGA aggregates I2C, SPI, GPIO, MDIO, and LED controllers into a memory-mapped, low-latency path, replacing fragmented sideband buses. Output states — optics reset and LPMode, LED levels, GPIO outputs — must survive Host CPU and PCIe link resets and only clear on a switch-level power cycle or an explicit software request.

Inventory is an Atomic Platform Entity (APE) tree. An APE is the smallest unit of hardware that platform software tracks: a FRU, a standalone PCBA, or several boards grouped as one logical APE when they are software-transparent. APEs form a tree rooted at a single Root APE, with IDPROM requirements at each node, making device enumeration a deterministic top-down traversal. You do not talk to a child until the parent is up. Hot-swap APEs need a presence GPIO; access when presence is de-asserted is prohibited.

The Root APE IDPROM sits on the Host CPU’s embedded I2C/SMBus so it is readable before the rest of the tree. The Platform Identifier IDPROM (product name, serial, asset tag) lives on the chassis or blade, never on a field-swappable part, and must be reachable from both BMC and Host. Formats are customer-specific: Meta EEPROM format v6 or ONIE TlvInfo. Product name from dmidecode -s system-product-name must match the Platform Identifier IDPROM. Discovery loads config from that name, not from the IDPROM, because the IDPROM’s bus and address are themselves platform-specific.

The worked example is Meta Minipack3. The Main Carrier Board is the root APE. The IOB FPGA on that board is the I2C/SPI/MDIO/GPIO fan-out. That is the “boot the same way” claim in operator language: same walk, different JSON.

On a switch-level power cycle, the BMC comes up by itself. The Host — CPU, ASICs, optics — stays off or in reset until the BMC, or the Host Bringup watchdog, turns it on. The watchdog’s default timeout is 5-minute. The BMC disables the watchdog once Host power-good asserts. If the Host is already on when the timer expires, the watchdog must not change the power state. First Host power-on: ASICs come out of reset without Host software; optics stay in reset until Host optics management takes them out; the ASIC must always enumerate on PCIe across Host CPU resets without software.

PSUs are PMBus-observable. AC configs must support N+1 redundancy or better. SPI flash is the preferred firmware path so flashrom and flashcp work. JTAG is not preferred; there is no standard Linux user-space ABI. Critical images get A/B banks and dual-path recovery. Host is the primary updater; BMC recovery is the fail-safe. The IOB ioctl header lives at fbiob-ioctl.h. The drivers are deployed across over 10 FBOSS platforms. Discovery code is platform_manager. The OCP tenets section says the same stack has proven deployment across over 10 production switch platforms, and that a configuration-driven design enables platform onboarding in under one day. Those are the spec’s numbers, not a measurement of my own.

The boot sequence in Section 14.2

The boot sequence in Section 14.2 is the part I would actually implement against. Platform Device Discovery loads a config file such as platform_device.json and walks the APE tree in a fixed order:

Step What happens
Platform Identification Retrieve the system name via dmidecode and load the platform-specific device configuration file.
APE Topology Construction Build a hierarchical inventory of Atomic Platform Entities according to the defined topology.
Device Enumeration Starting from the Root APE, traverse the hierarchy, read each APE’s IDPROM to verify board revisions, and initialize I/O controllers and client devices.
Stable Mapping Creation Generate stable symbolic links (e.g. /run/devmap/xcvrs/xcvr_io_1 → /dev/i2c-15) so platform services never depend on dynamic Linux device indices.

SAI made the forwarding API reusable. OSPA is trying to do the same for the software you run before the first packet — the way AICR froze a contract for GPU Kubernetes recipes, except here the unit is a switch SKU, not a cluster recipe. The IOB drivers and Minipack3 walk are the evidence that this is not a greenfield slide. Until a second ODM SKU boots through that same walk, I would read OSPA the way I read ESUN 1.0: a vendor-neutral reference you can design against, with working FBOSS code behind the IOB chapter, and with the Foundation review stamp still on the cover.
